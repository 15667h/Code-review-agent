# Margin · 从「代码审查工具」到「可插拔研发助手」

原型设计说明 · 供过目

---

## 一、设计简报（先明确，再动手）

| 项 | 内容 |
|---|---|
| 产品 | Margin —— 一个工作台，多个研发辅助 Agent |
| 本轮新增 | **架构设计助手**（第二个 agent） |
| 用户 | 计算机方向学生 / 求职者，本机长时间使用；偶尔给同学演示 |
| 任务 | ① 在同一处切换不同助手 ② 每个助手有自己的输入方式与产出形态 ③ 能接入新助手 |
| 调性 | 克制的工程感。已确立的「编辑部校样台」不推翻 |
| 模式 | `overhaul`：**信息架构重做，视觉语言保留**（design-taste-plus §6） |

**必须解决的核心矛盾**：现在整个 UI 是照着「发现列表」写死的（发现卡片、严重级别筛选、
批注边）。架构助手的产出是**分层图 + 组件清单 + 决策记录**，跟发现列表毫无关系。
所以这一版的重点不是「加一个页面」，而是**把「产物形态」变成 agent 自己声明的东西**。

## 二、两个关键决策

### 决策 1：Agent 切换放在哪

**选定：左侧 Agent 轨道（56px）+ 上下文栏**

```
┌────┬──────────────┬────────────────────────────────┐
│ 审 │ 对象列表      │ 顶栏：当前对象 + 状态            │
│ 架 │  ▸ payments  ├────────────────────────────────┤
│    │    #482 …    │                                │
│ +  │              │  工作台（产出形态随 agent 变）   │
│56px│   268px      │                                │
│    │              ├────────────────────────────────┤
│    │              │  输入坞（骨架共享，方言随 agent）│
└────┴──────────────┴────────────────────────────────┘
```

理由：agent 是**身份级**概念，不是视图级。它能不能被一眼看见，直接决定「可插拔」这个卖点
是否成立。轨道底部那个 `+` 就是「接入新助手」的入口。

另外两个候选（也画出来，便于比较）：

```
方案 B：顶栏 tab                         方案 C：首页卡片墙
┌────────────────────────────────┐      ┌──────────────────────────────┐
│ [审查][架构][测试]  仓库·分支    │      │      你要做什么？             │
├──────────┬─────────────────────┤      │ ┌────────┐ ┌────────┐        │
│ 仓库      │                     │      │ │ 代码审查│ │ 架构设计│        │
│ ▸ pay…   │  工作台              │      │ └────────┘ └────────┘        │
├──────────┴─────────────────────┤      │ ┌────────┐                   │
│ 输入坞                          │      │ │+ 添加助手│                  │
└────────────────────────────────┘      └──────────────────────────────┘
```

- B 省一层宽度，但 tab 的语义是「同一对象的多个视图」，agent 是**不同工具**，语义错位；
  且助手变多会挤掉顶栏里的仓库名与状态。
- C 可发现性最好，但两个助手互相切换时要来回跳转，日常使用成本高。

**结论**：A 作为主结构；C 的卡片墙**不以独立页面存在**，改造成轨道底部 `+` 打开的
「助手」浮层 —— 保留可发现性，不增加一次跳转。

### 决策 2：架构助手的产出长什么样

不能是「发现卡片换层皮」。架构方案的本质是**分层结构 + 组件职责 + 决策理由**，
所以做成三分区，且**图与清单双向绑定**：

```
┌───────────────────────────────┬──────────────────┐
│ 设计目标与约束（agent 复述，可纠偏）│                  │
├───────────────────────────────┤  组件详情         │
│                               │  （跟随左侧选中）  │
│   分层架构图（可点选节点）      │                  │
│   ┌ 接入层 ──────────┐         │  Order Service   │
│   │ [Gateway] [Auth] │         │  职责 / 接口 /     │
│   └────────┬─────────┘         │  依赖 / 失败模式   │
│   ┌ 业务层 ▼─────────┐         │  为什么这样切      │
│   │ [Order][Payment] │         │                  │
│   └────────┬─────────┘         │                  │
│   ┌ 数据层 ▼─────────┐         │                  │
│   │ [MySQL][Outbox]  │         │                  │
│   └──────────────────┘         │                  │
├───────────────────────────────┴──────────────────┤
│ 关键决策（ADR）：选项 A / 选项 B / 选择 / 代价       │
├──────────────────────────────────────────────────┤
│ 开放问题（agent 主动暴露不确定）                    │
└──────────────────────────────────────────────────┘
```

点一个组件 → 相关连线高亮 + 右侧换成它的详情。这是这个面板的记忆点，
也是「图纸」方言（网格底、分层色阶）与「校样台」方言（批注边、行号列）的区别所在。

## 三、设计系统

### 视觉叙事：一个工作台，两个房间

| | 代码审查（已存在） | 架构设计（新） |
|---|---|---|
| 隐喻 | 校样台 | 制图室 |
| 强调色 | 深青 `#0f6b5c` | 普鲁士蓝 `#1c3f6e`（晒图纸色） |
| 纹理 | 批注边（2px 竖线 + 行号列） | 网格底（方格纸）+ 分层色阶 |
| 首要产出 | 发现列表（可筛选、带证据） | 分层图 + 组件 + 决策 |

**关键做法**：强调色不是写死的两套样式表，而是 agent 声明的一个变量。

```css
[data-agent="review"]    { --agent: var(--accent); }
[data-agent="architect"] { --agent: #1c3f6e; --agent-soft: #e8eef7; }
```

整个界面（轨道高亮、顶栏标记、按钮、连线、选中态）都吃 `--agent`。
**接入新 agent 时，换一个色值即可，不用碰任何组件样式** —— 这是「可插拔」在视觉层的落地。

普鲁士蓝的选取理由：它是工程图纸的固有色，与深青同属冷色家族（不会显得像另一个产品），
且与已有的四个语义色（阻断红 / 警告琥珀 / 建议石板紫 / 通过绿）都不撞。

### 沿用不动的部分

- 冷纸底 `#f4f6f5` + 偏青墨色 `#0e1a18`，不用纯黑纯白
- Fraunces（衬线标题）+ Instrument Sans + JetBrains Mono，**不用 Inter**
- 4px 基准但不等距的间距节奏、同心圆角 `outer = inner + padding`
- 动效只用于状态变化，命名属性、不用 `transition: all`

## 五、需要你确认的假设

1. **轨道是否值得占 56px？** 若你更在意横向空间，我改成「顶栏图标 + 下拉」（方案 B）。
2. **架构助手的产物是否要能导出？** 原型里留了「导出方案」按钮，但没做流程。
3. **「开放问题」这一节是否保留？** 它让 agent 主动暴露不确定，我觉得对架构设计很关键，
   但如果嫌啰嗦可以砍掉。
4. **可添加助手清单**里我放了三个假想项（测试生成 / 文档 / 性能分析）。
   这是演示「可插拔」用的，实际要接哪些由你定。

## 六、原型怎么看

打开 `mockups/index.html`（纯静态，双击即可）：

- 点左侧轨道的两个图标 → 切换助手，观察**整个界面的强调色与产出形态一起变**
- 点轨道底部 `+` → 助手浮层（可发现性）
- 在架构助手里**点左边的组件节点** → 右侧详情跟着换、相关连线高亮

  它钉在视口底部，滚轮滚的是上面的内容区，它自己不动
- 审查助手沿用现有布局，用来验证「新结构没有破坏旧功能」

带参数可以直接落到某个房间：`index.html?agent=architect` / `?agent=review`。
（URL 反映状态 —— 这是 web-design-guidelines 明确要求的一条。）

## 七、响应式：三个断点

| 断点 | 变化 | 为什么 |
|---|---|---|
| ≤1180px | 架构图与组件详情由左右并排改为上下堆叠 | 并排时两边都太窄，图里的节点会挤到换行 |
| ≤960px | 顶栏元信息（3 层 / 8 组件 / 2 项待确认）整块收起 | 它是三段并列的短标签，空间不够时会被逐字压成竖排条 |
| ≤900px | 上下文栏改为**抽屉**，顶栏左侧出现开关 | 不能只 `display:none` 藏掉 —— 那样就没有「切换任务」的入口了 |
| ≤720px | 输入坞的模型名收起，只留图标 | 让位给输入框 |
| ≤480px | 任务标题与连接状态的文字收起，连接状态只留状态点 | 360px 这条线上，顶栏右侧会把整行顶出视口 |

连接状态收起文字后，用 `role="status"` + `aria-label="后端已连接"` 把信息留住，
不因为视觉上压缩而丢掉可达性。

架构图里，层名走**左侧栏位**（84px），节点全部排在右侧 —— 这样跨层连线只落在节点区，
不会横穿每一层的说明文字。跳层依赖（接入层直连数据层）用**直角走线 + 虚线**从左侧走廊绕行，
线型本身携带信息（图例在图下方说明）。

## 八、这一轮实测挖出来的问题（都已修）

原型不是画完就交。我用真实点击与几何探针跑了一遍，挖出这些：

1. **同层连线从中间的节点身上穿过去** —— `order → inventory` 两者之间夹着 `payment`，
   原来的浅弧只下沉 16px，仍在节点高度范围内。改为：两点之间夹着别的节点时，
   走直角从节点行**下方**绕行；相邻节点才用浅弧。
   探针按 3px 一步采样 12 条连线，现在报告「没有连线穿过无关节点 / 层名 / 画布边界」。
2. **跨层连线横穿层名文字** —— 原来层名在节点上方，进层的线必然压过去。改为左侧栏位布局。
3. **窄屏没有切换任务的入口** —— 上下文栏被 `display:none`，但没留开关。
4. **窄屏顶栏被压成一字一行的竖排条** —— 三段元信息不换行又不收缩。
5. **375px 下「发现 4 条发现，涉及 2 个文件」被压成一字一行** —— `card__head` 是
   `justify-content: space-between` 的 flex，标题一侧被筛选按钮挤到只剩一个字宽。
   加 `flex-wrap: wrap`，并给 `.chip` 加 `white-space: nowrap`（「导出方案」曾被折成两行）。
6. **360px 下顶栏右侧溢出 17px** —— 连接状态 + 模型按钮。
7. **输入坞被推到视口外，滚轮也够不着**（用户实测反馈：「没有 agent 对话框吗？鼠标上下滑动呢？」）
   —— 这是最严重的一个，因为它让整个原型看起来少了最重要的东西。
   根因在骨架：`.app` 只定义了 3 列、**没有定义行**，于是那唯一的隐式行是 `auto`，
   被内容撑到 1725px。容器本身仍是 `100dvh`（所以量计算高度看不出任何异常），
   但 `.stage` 长到 1725px，输入坞落在 y=1546；而 `body{overflow:hidden}` 会传播到视口，
   滚轮滚不动文档 —— 输入坞存在、却永远够不着。同时 `.work` 的高度也等于内容高度
   （1485/1485），所以它自己也不滚动，滚轮在内容区上完全没反应。

   修法：`.app` 补 `grid-template-rows: minmax(0, 1fr)` + `overflow: hidden`，
   并给 `.stage` / `.context` 补 `min-height: 0`（grid 项的 `min-height` 默认是 `auto`，
   等于内容高度，会绕开行高的约束）。

   对照：真实应用（`styles/app.css`）没有这个问题 —— 它把 `height: 100dvh` 放在
   **grid 项 `.stage`** 上，硬撑住了。原型把 `100dvh` 放在**容器 `.app`** 上，
   行高就失控了。同一条规则写在容器上还是写在项上，结果完全不同。

### 测量上的三个坑（记下来，免得下次再踩）

- **Chrome 无头模式的窗口有最小宽度（约 500px）**。用 `--window-size=430` 截图时，
  页面其实按 500px 布局、再被裁成 430px —— 看起来像「窄屏溢出」，其实是截图工具造成的假象。
  要量真实窄屏，得用一个显式设定宽度的 `<iframe>` 把页面装进去。
  我一开始就是这么误判了一次，差点去改一堆没问题的样式。
- 探针里操作完**必须按选择器重新查询节点**：一次点击会重绘列表，
  拿着旧节点读属性会把「生效了」读成 `false`。
- **固定 `setTimeout` 在虚拟时钟下会在样式生效之前就量**。查第 7 条时，
  第一版探针每档都报「输入坞在 1546」，连 `viewportH=900` 那档也是 —— 数字一模一样，
  看起来像铁证，其实是它在 CSS 应用前就量了。
  改成「等一个可证伪的条件」（`.app` 的计算高度等于 iframe 视口高度）才算就绪，
  并且把「计算高度」和「rect 高度」分开报，才看出真正的矛盾：
  容器 654、行高 1725。
  **先确认测量工具本身可信，再信它的结论** —— 这已经是同一个教训的第三次了。

- 验证「鼠标上下滑动」不能用页面内 `dispatchEvent` 造合成事件 ——
  合成事件不触发滚动，拿它测滚轮等于自欺。真正管用的是 CDP 注入
  （`Input.dispatchMouseEvent`）：脚本留在 `.workbuddy/tools/ui-tests/`
  （`wheel-test.js` / `geom-test.js`，需要 puppeteer-core，不入库）。
