# hunter（安全狩猎）· 实现说明

> 2026-10-25 实现。第五个 Agent，`outcome = threat_model`。
> 定位：找**规则抓不到的逻辑级漏洞**。

---

## 一、为什么需要它（这次有硬数据）

先把靶场标注摊开看。`examples/m1-order-desk` 有 27 条标注：

| 类别 | 条数 | 规则引擎能抓吗 |
|---|---|---|
| AUTHZ（越权） | 6 | ❌ 完全不能 |
| CONC（并发竞态） | 6 | ❌ 完全不能 |
| BOUND（业务边界） | 4 | ❌ 完全不能 |
| CONSIST（状态一致性） | 1 | ❌ 完全不能 |
| ERR（错误处理） | 4 | 部分 |
| SEC / RES / PY | 6 | ✅ 大部分能 |

**规则最多覆盖 5 条，剩下 22 条全在逻辑层。**

不是规则写得不够多 —— 是这类缺陷**没有可匹配的文本特征**：

```python
def get_order(order_id):
    return store[order_id]          # 看起来完全正常，没有任何危险函数
```

问题不在这一行，在于**缺了一行**：没有比对 `order_id` 属不属于当前用户。
正则无法检测「缺失」，只能检测「存在」。

只有先想清「这个系统的业务规则该是什么」，再拿代码去比对，才能发现。
这就是 hunter 的全部价值。

## 二、它与 review 的边界（最容易混）

| | review / 规则引擎 | hunter |
|---|---|---|
| 能发现 | **模式级**：危险函数、可疑字符串 | **逻辑级**：业务规则没被守住 |
| 例子 | `eval()`、`pickle`、`shell=True`、明文密钥、SQL 拼接 | 按 id 取数据不校验归属、锁挂在每请求新建的对象上、只校验状态不校验金额 |
| 靠什么识别 | 正则匹配文本特征 | 先想清「规则该是什么」再比对 |
| 产出 | `finding`（有 blocker/warn/note） | `threat`（有 category，**没有严重级别**） |

**同一条规则在 prompt 里反复强调**：看到 `eval` / `pickle` / 明文密钥，
不要报 —— 那是审查助手的活儿，重复报只会让同一问题在 PR 上出现两次。

规则重叠时填 `overlaps_rule`，工具会提示「去掉它」。

## 三、核心约束：攻击路径必须可重放

`attack_path` 是这份产出的可复核性所在。

```
✗ 存在越权风险                        ← 没有动作，没有结果
✗ 权限校验不足，可能被利用             ← 同上
✓ 任意已登录用户遍历 order_id → GET /orders/<id> → 返回他人订单明细
✓ 两笔并发退款同时读到 refunded=0 → 各自写回 100 → 实际退了 200 但只记 100
```

校验判据：**至少含一个动作词**（请求/调用/并发/构造/遍历/传入…）+ 长度 ≥ 12。
只写「可能存在风险」的会被拒，错误信息里给出可重放的示范
（不给示范的话，模型只会改措辞而不改内容）。

`impact` 同理必填：「存在信息泄露风险」不算，要写「可读取全站任意客户的订单、
地址与手机号」。**写不出具体危害，通常说明这个「漏洞」其实不成立。**

## 四、两个机械清点工具（候选生成器，不是判定器）

模型很难自己做完一件事：**把一个仓库的所有入口列出来，标注谁有校验谁没有**。
这件事机械扫描一秒出结果，而且它的产出是推理的靶子。

### `check_authz_surface`

列出所有对外入口 + 附近有没有鉴权代码，并**找出同一文件里鉴权不一致的地方**。

「同文件不一致」是最像漏洞的信号 —— 一个文件里 `purge` 有 `require_ops`、
批量发货没有，那通常不是有意的，是漏写。

**实测教训（两个）**：

1. **只认框架写法会整个失明**。第一版只匹配 `@app.get` / `@route`，
   而靶场用自研的 `handle_*` 函数 + 手写分发表 —— 一条入口都没找到。
   自研分发层在真实项目里很常见，必须同时认命名约定（`handle_` / `api_` / `view_`）
   和分发表里的路由键。

2. **固定窗口会污染判定，而且方向是「漏报」**。第一版往上 6 行、往下 8 行，
   于是上一个函数的窗口盖住了下一个函数体里的 `require_ops` ——
   **无校验的入口被标成「有校验」**。这比误报更危险：它会让人相信这里已经守住了。

   修法：窗口按函数边界截取（往回找到上一个 `def`，往前找到下一个 `def`）。
   修完入口数从 23 降到 12（噪音减半），而「无校验」的 7 个精确命中靶场缺陷。

### `check_concurrency_surface`

列出共享状态的「读-改-写」位置，标注附近有没有锁。

它**不能**判断锁的作用域对不对 —— 而最常见的竞态 bug 恰恰是
「锁挂在每请求新建的对象上，有锁等于没锁」。这一条必须读代码。

两个工具的输出里都明确写了「这不是漏洞结论」。
不写的话模型会把「没看到鉴权代码」直接当成「有越权」，
报出一堆评审一眼就能否掉的条目 —— 比不报更伤信任。

## 五、六个威胁类别

| category | 判定要点 |
|---|---|
| `authz` | 按 id 取数据不校验归属；权限函数恒真；只在部分入口校验；同文件不一致 |
| `race` | 读-改-写非原子；**锁作用域错误**；两步之间可被插入 |
| `boundary` | 只校验状态不校验金额；数量可负；分页 limit 为负；状态机允许非法跃迁 |
| `crypto` | 非常量时间比较；密钥写死或缺省回落；签名缺算法字段 |
| `consistency` | 退款不改订单状态；库存与账目各自更新导致失衡 |
| `injection` | 路径穿越、模板注入等非 SQL 的注入面 |

## 六、真实模型实测（deepseek-v4.1-flash）

**输入**：目标里给出四个角色（匿名 / 普通用户 / 客服 / 运营）。
**输出**：18 轮 / **85 秒** / **17 条威胁** / **0 条缺攻击路径**。

类别分布：`boundary=6 / authz=4 / consistency=3 / race=3 / injection=1`。

### 五条抽查（全部命中靶场标注）

```
[authz] 客服权限判定恒真：座席可查看任意客户的订单
  app/service.py:265
  路径：座席以 X-Operator: <自己工号>、X-Role: agent 调用
        GET /admin/staff/orders/<order_id> 并遍历 order_id
        → handle_staff_view 取 staff_id 与 role 后调用 ...
  影响：任意客服座席可读取全站任意用户的订单归属人、状态与应付金额，
        绕过「座席只能看所辖客户」的隔离；_STAFF_ZONES 关系维护形同虚设

[authz] 订单详情、支付、取消三个前台入口不校验订单归属（IDOR）
  app/api.py:71
  路径：普通用户以自己身份请求 GET /orders/<他人order_id>
        → handle_get_order 调 service.get_order(order_id)，
        内部只用 wb.orders.get(order_id)，从不比对 request.user_id
  影响：可读取任意用户订单明细；可越权把他人订单置为已支付
        （未真实付款却进入可发货状态），或取消他人订单造成库存与账本错乱

[authz] 运营导出与账户摘要接口无任何鉴权，owner 取自请求参数
  app/admin_api.py:94  |  匿名访客（无需任何身份）
  路径：未认证请求 GET /admin/orders/export?owner=u1&rows=1000
        → handle_export 没有校验，直接取 owner 参数 ...
  影响：未认证即可读取任意用户全量订单记录，可作为后续越权操作的订单号来源

[authz] 批量发货入口缺少角色校验，同文件其他写操作均有校验
  app/admin_api.py:49
  路径：以 X-Role: visitor 请求 POST /admin/orders/bulk-ship ...
  影响：低权限/未认证调用方可批量把任意 PAID 订单置为已发货，
        副作用是逐单向承运商真实打单，不可撤销

[boundary] 下单接受客户端传入的单价与优惠额，应付金额可被压到 0
  app/service.py:55
  路径：构造 unit_price=100（1 元，服务端不校验是否等于 SKU 目录价）
        且 coupon=50 → place_order 中 pricing.clamp_discount(50, 1) ...
  影响：可自定成交价与优惠额，把应付降到 0；又因 payable 是退款上限，
        也影响后续退款核算
```

**每条的路径都具体到请求头、参数、函数名** —— 可以照着重放。
这正是「规则写不出来、只有推理才能得到」的那一层。

## 七、离线模式

`HeuristicModel._complete_hunt`：调 `check_authz_surface` → 为无鉴权入口登记 `authz` 威胁。

**离线产出明确标注是候选**：每条 `preconditions` 都写着
「离线模式只检测到入口附近没有鉴权代码，**未验证**校验是否在更外层完成」。

**且 summary 明确说了离线做不到什么**：

> 离线模式无法判断：权限函数逻辑错误（如恒返回 True）、跨文件的归属校验缺失、
> 并发竞态、业务边界。这些问题需要真实模型读懂业务语义，或人工审计。

实测：m1 靶场上离线跑出 9 条 authz 威胁，命中 `bulk_ship` / `attach_items` /
`export` / `staff_view` / `digest` —— 正好是标注里的 AUTHZ004/005/006 + BOUND003/004。

## 九、已知边界（如实说明）

1. **越权检测依赖「角色定义」**。目标里不说明有哪些角色、各自该做什么，
   越权类问题很难被找到 —— 因为「越权」的定义就是「某角色做了它不该做的事」。
   这不是缺陷，是这类审计的前提。
2. **两个清点工具是启发式**。自研路由框架识别不到；锁的作用域判断需要读代码；
   非 Python 语言没有对应的形态识别。
3. **不判断修复方案**。只报告问题。修复属于 planner / 人工。
4. **威胁没有严重级别**。用 category 分类而不是 blocker/warn ——
   因为「越权」和「弱哈希」的严重程度取决于业务，静态定级会误导。
   排序按类别（authz/race 在前），含义是「最常被利用」而不是「最严重」。
5. **不做漏洞利用验证**。没有动态执行，所有结论都是静态阅读得出。
