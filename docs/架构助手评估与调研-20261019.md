## 一、互联网调研：这个方向的水位

### 1.1 学术界已有**可量化的**架构恢复指标

| 工作 | 做法 | 指标 |
|---|---|---|
| **Semref**（arXiv 2607.23774） | LLM + 依赖分析，自动精修传统架构恢复工具的输出 | **MoJoFM**（模块聚类相似度）、**a2a**（相邻度）、**ARI**、a2a_adj、c2c_cvg |
| **ROS2 架构恢复**（arXiv 2605.20055） | 两阶段：先产出中间 JSON 制品（节点清单 / launch 依赖），再合成 PlantUML | 以专家手工模型为 GT，算 **precision / recall / F1**（ACD 1.0/1.0/1.0，CCD 1.0/0.95/0.98） |
| **Code of Theseus**（arXiv 2610.20068） | 从紧凑仓库表示恢复「意图 + 需求 + 架构」三份对齐制品 | **模块 F1 0.54 → 0.63**（用恢复出的架构重建代码，比只看测试更接近原结构） |

**共同点：都有 ground truth（专家模型或原结构），都能算 F1。**
Semref 的做法特别值得抄：**不推翻重来，而是拿 LLM 去精修已有恢复结果的错误**。

### 1.2 工业界的共识与警告（对我们最有用的部分）

**「AI 当挑战者，不当作者」**（Akash Talole / metacto）：
- 让 AI 找风险、找遗漏的备选、找边角情况 —— 这些它确实强
- 不让 AI 拍板：它不知道你的预算、团队技能、遗留系统、合规要求（**constraint blindness**）
- 它按「什么是常见的」训练，所以倾向**流行默认值**，与「没有最好的，只有合适的」直接冲突

**ADR 的标准结构**（多位作者一致）：
`Status / Context / Decision Drivers / Considered Options / Decision Outcome /
Consequences / Validation Plan / Links`
其中 **«Considered Options» 不能是稻草人（not straw men）**，**«Consequences» 要含成本、风险、迁移工作与后续检查**。

**一个关键的负面警告**（jeffbailey.us）：
> 模型能为几乎任何选择写出流畅的理由，把「单纯的偏好」包装成「严谨的权衡」——
> 表面通过了「靠力量而非偏好」的标准，底下其实没通过。

这是架构助手最核心的失败模式，比「事实错误」更难识别。

**Groundedness 的可操作定义**（多篇一致）：
把输出拆成**原子声明（atomic claims）**，逐条对证据判「是否被蕴含（entailed）」。
报告形式是 `2/5 claims grounded`，而不是一个笼统的 0.92 均值。
**LLM judge 抓不住伪造引用比字符串匹配可靠得多** —— 引用必须先过机械校验。

### 1.3 一个反直觉的事实

**ProgramBench**（Meta AI，200 个任务，要从二进制重建整个软件）：
最好的模型（Claude Opus 4.7）只有 **3.0% 部分解决，0% 完全解决**。
结论：**架构级推理是全行业未解难题**，比代码审查难得多。
这意味着我们的期望值要现实：目标不该是「架构设计得对不对」，
而该是「这份方案可不可评审、有没有凭空捏造」。

## 二、本项目调研：实测，不自述

### 2.1 现状（代码事实）

| 项 | 值 |
|---|---|
| 产出类型 | `blueprint`：layer / component / decision / open_question |
| 架构特有工具 | `record_layer` / `record_component` / `record_decision` / `record_open_question`（4 个） |
| 只读保证 | `can_edit=False`，`run_agent` 里 `_enforce_read_only` 硬拒任何 `risk>=MEDIUM` 工具 |
| 案例 | E1 pluggy 36 文件 7.2k 行 / E2 requests 37 文件 12k 行 / E3 celery 447 文件 123k 行 |
| 现有评估 | `arch-cases/RESULTS.md`：三档「照妖镜」定性通过；E1 15 轮撞上限、E3 复跑撞上限 |

已有评估的长处：**分档有权威依据**（System Design Primer / techscreen / tutorialq 的共识刻度），
**上了「照妖镜」**（每个案例预写必须答对的架构事实），**如实声明了样本量不足**。

### 2.2 我这次独立跑的 E1 实测

命令：`--agent architect -r arch-cases/e1-pluggy/repo --max-iterations 20`
耗时 3 分 7 秒，产出 **5 层 / 13 组件 / 6 决策 / 6 开放问题**。

**产出质量观察（读完实际内容后）**：
- 明确指出了 pluggy 的垫片残留：`_manager.py:19-28` 仍从 `._hooks` 垫片取名，
  形成内层对门面的**反向边**，并登记为开放问题 + 给出机械改法。
- 主动交代了两条没做到的地方（一处重复提交被拒、下游项目未实际运行）。
- **这种「主动暴露没做到的部分」的行为，恰恰是可信度最需要的东西。**

### 2.3 但引用可核验性很差（本文最重要的发现）

用脚本抽取产出里所有 `file:line` 引用并逐个核对：

| 指标 | 值 |
|---|---|
| 引用总数 | **55** |
| 精确完整路径 | **5**（9%） |
| 需按 basename 模糊匹配 | **48**（87%） |
| 同名文件导致无法定位 | **2**（`__init__.py` 有 2 个同名） |

**根因不是模型偷懒，是结构性问题**：

```python
Component:      name, layer, role, responsibility, interfaces, depends_on,
                failure_modes, rationale, id, fingerprint
Layer:          name, purpose, hint, order, id, fingerprint
DecisionRecord: title, decision, rationale, alternatives, consequences, id, fingerprint
OpenQuestion:   question, why_it_matters, blocking, id, fingerprint
```

**四个结构里没有任何「证据 / 出处」字段。** 引用只能写在自由文本（`rationale`、`detail`）
里，于是：
1. 模型可以写 `_caller.py:127` 而不写完整路径（它以为是显然的）；
2. 事后**无法机械核验**这些引用；
3. 前端也无法把引用做成可点击跳转。

对比审查助手：它有 `verify_citations` + `cross_check_line_content` + 判官层三层核验。
**架构助手一层都没有。** 这是两个助手之间最大的能力落差。

### 2.4 与业界标准的差距

| 维度 | 业界做法 | 本项目 | 差在哪 |
|---|---|---|---|
| 量化评估 | MoJoFM / a2a / 模块 F1（有 GT） | 「照妖镜」定性通过 | **没有可复算的分数** |
| 引用核验 | 强制结构化引用 + 机械校验 | 引用混在自由文本里 | **无法核验（本次实测 9% 可精确定位）** |
| 「权衡是否真实」 | 专门警告：模型会把偏好包装成权衡 | 提示词要求写「代价」，但无校验 | 无法区分真权衡与漂亮话 |
| 备选方案 | 必须非稻草人 | `alternatives` 字段存在 | 无「稻草人检测」 |
| 约束处理 | 缺约束要显式登记 | 提示词已要求（写得好） | ✅ 这点做对了 |
| 只读边界 | 少见 | 硬契约 | ✅ 这点做得比业界好 |
| 中间制品 | 先结构化中间 JSON 再合成 | 直接产出结构 | 大体相当 |

## 三、完成度评分（诚实版）

| 维度 | 评分 | 依据 |
|---|---|---|
| **工程完备度** | ★★★★☆ | 只读硬契约、可插拔、测试覆盖、错误信息四层 |
| **产出结构设计** | ★★☆☆☆ | 四类产出语义清晰，但**缺证据字段**是硬伤 |
| **可核验性** | ★☆☆☆☆ | 55 处引用只有 5 处可精确定位；无任何自动核验 |
| **评估严谨度** | ★★★☆☆ | 分档有依据、有照妖镜、如实声明样本量；但**无量化分数** |
| **提示词质量** | ★★★★☆ | 「不许用肯定语气掩盖不确定」「只有好处没有代价不是选择」——写得很好 |
| **与业界差距** | 中等偏上 | 只读边界与诚实约束超出多数工具；量化评估与引用核验落后 |

**一句话**：这是一个**工程上相当扎实、认知上很清醒**（知道自己不确定什么）的系统，
但它**产出的东西无法被机械验证** —— 而这恰恰是架构分析最需要的。

## 四、增强路线（按性价比排序）

### P0：给产出加「证据」字段 + 引用核验（最高性价比）

给 `Component` / `Layer` / `Decision` 加 `evidence: list[str]`（`file:line` 列表，要求完整路径），
然后复用审查助手已有的 `cross_check_line_content` 做核验：
- 文件是否存在
- 行号是否越界
- 那一行的内容是否与「这个组件/这条决策」的描述相关

**预期**：把可精确定位率从 9% 提到 80%+，并把「凭空捏造的组件」直接拦掉。
**成本**：字段 + 提示词 + 核验函数 + 测试，约 1 天。**这是最该先做的。**

### P1：权衡真实性核验（打「偏好包装成权衡」这个痛点）

业界明确警告这个失败模式，但**几乎没人给解法**。可行做法：
- 要求 `alternatives` 每条必须写「放弃它的具体原因」+ 至少一条**它自己的优点**（稻草人没有优点）
- 确定性检查：`consequences` 里必须出现负面词（成本/风险/复杂度/延迟/迁移），否则提示「疑似只写了好处」

这条是**微创新点**，成本低（纯文本规则），而且直指业界公认痛点。

### P2：量化评估（用业界指标）

给每个 arch-case 写一份「专家参考蓝图」（`reference.json`），然后算：
- 组件集合的 **precision / recall / F1**（按 name 归一化后匹配）
- 依赖边的 F1
- 分层结构的 **MoJoFM 近似值**

**成本**：主要是人工写 3 份参考蓝图（每份 30–60 分钟）。**收益**：把「定性通过」变成可复算的数字。

### P3：中间制品（借鉴 ROS2 那篇的两阶段）

先让模型产出「符号清单 JSON」（类/函数/导入关系，可用 `read_symbols` 机械得到），
再让它基于清单做分层与组件划分。ROS2 那篇正是靠这一步把幻觉压下去的。
**成本**：中等（要改工作流，不只是加字段）。

### P4：多档难度收敛问题（E1/E3 撞迭代上限）

现有结果里 E1 有一次 15 轮撞上限、E3 复跑 24 轮撞上限。
需要的是**预算管理**（先扫结构再决策，而不是边读边画），而不是简单加轮数。

## 五、结论

**能增强，而且 P0/P1 是低成本高收益的。**

但要说清期望：本项目的架构助手在**工程纪律**（只读、诚实登记不确定）上已经超过不少商用工具，
真正的短板是**「产出的可验证性」**——这不是模型能力问题，是**数据结构和流程设计问题**，
所以可以靠工程手段解决，不需要换更强的模型。

与审查助手的差距很清楚：审查有「位置核验 + 内容核验 + 判官」三层，
架构**一层都没有**。补上这三层里的前两层，架构助手的可信度会有质的改变。
