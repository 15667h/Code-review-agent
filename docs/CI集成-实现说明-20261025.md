> 2026-10-25 实现。让 Margin 从「本地手动跑的工具」变成「跑在 PR 上的验证层」。
> 零新增依赖（`requirements.txt` 未改动）。

---

## 一、为什么这件事比加新 Agent 更紧急

调研里所有对标产品（Qodo / CodeRabbit / Greptile / Copilot / SonarQube）**都跑在 PR 上**。

「独立验证层」的价值**在流程节点上，不在本地工具上**：
- 本地工具：什么时候跑取决于人的记性
- PR 节点：每次提交都过一遍，且结果留在系统里可追溯

没有 CI 集成，我们只是一个「能演示的本地 CLI」。

## 三、五个关键设计决定

### 1. 为什么要 SARIF 而不是只贴评论

GitHub 原生识别 SARIF。上传后结果进 **Security → Code scanning**：
- 可以按规则筛选、可以标记误报、可以看历史趋势
- 修复后自动消失（靠指纹匹配）

只贴评论的话，同一个问题在每次 push 后重复出现，且无法标记「这个我看过了」。

### 2. 严重级别不注水

| 我们 | SARIF level | GitHub 上的表现 |
|---|---|---|
| blocker | `error` | 红色，可让 check 失败 |
| warn | `warning` | 黄色 |
| note | `note` | 蓝色/灰 |

**刻意不把 warn 提成 error。** 一旦 warn 也标红，真正的阻断项被稀释，
开发者会对整片红色脱敏 —— 那等于关掉了这个检查。

### 3. 指纹不含行号

```python
指纹 = hash(文件 + 标题归一化)   # 不含 line
```

GitHub 用指纹判断「这是不是上次那个问题」，从而支持「已忽略」「已修复」。
带行号的话，代码往上挪几行就被当成新问题，之前标记的误报全部失效。

### 4. 只报改动范围，不报历史遗留

这是 CI 集成的**核心取舍**。实测：

```
全仓扫描：3 条历史遗留（2 个硬编码密钥 + eval）
本次 PR：只改了 app/another.py（无害）
```

| | 输出 |
|---|---|
| 不过滤 | PR 上 3 个红点，全都与本次改动无关 |
| 过滤后 | **0 条** —— 信号是「这个 PR 没引入新问题」 |

不过滤的后果很具体：开发者看到一堆与自己改动无关的红色，
第一反应是把这个检查关掉。这正是「AI 审查变成噪音」的典型路径。

**退出码也随之改变**：按**过滤后**的结果算，不是按全仓。
CI 要拦的是「这个 PR 引入了阻断级问题」，不是「仓库历史上有阻断级问题」——
后者会让任何 PR 都过不去。

### 5. 没配 API Key 时不让 CI 变红

```yaml
if [ -z "${LLM_API_KEY:-}" ]; then
  echo "未配置 LLM_API_KEY，跳过 AI 审查（规则扫描结果仍然有效）"
  exit 0
fi
```

开源项目的 fork PR 拿不到 secrets。如果这里硬失败，
**所有外部贡献都会被一个「配置缺失」卡住** —— 那是把基础设施问题伪装成代码问题。

规则扫描（确定性、秒级、不需要模型）永远跑。

## 四、workflow 的 10 个步骤

```
1. 检出（fetch-depth: 0，需要完整历史算 diff）
2. 安装 Python
3. 安装依赖（只 pip install -r requirements.txt —— 平台核心零依赖，别在这加东西）
4. 评估改动规模
5. 提示 PR 过大（> 3000 行）    ← 条件步骤
6. 规则扫描（确定性，无需模型）
7. 上传 SARIF（if: always()）
8. AI 审查（需要 LLM_API_KEY）   ← continue-on-error
9. 上传 AI 审查 SARIF
10. 发评论（一条，不刷屏）
```

### 三个容易做错的地方

**① `if: always()` 不能省。**
即使第 6 步因为发现阻断级问题返回非 0，第 7 步也要执行。
否则「有问题的 PR」反而**看不到问题**（因为 job 失败后续步骤被跳过）。

**② 权限最小化。**
```yaml
permissions:
  contents: read          # 不给 write —— 即使被供应链攻击也推不了代码
  pull-requests: write    # 只需要发评论
  security-events: write  # 上传 SARIF
```

**③ 3000 行闸门不是为了省钱。**
超过这个规模的 diff，模型会「跳读」但输出看起来依然完整 —— **那比不审更危险**。
所以超阈值时提示拆分 PR，而不是硬审。

## 五、实测踩到的三个 bug

### bug 1：`--scan-only` 静默忽略 `--diff`

传了 `--diff HEAD~1`，但 `--scan-only` 分支**根本没读这个参数**，
仍然输出全仓结果、退出码照旧。

**这比报错更糟**：CI 里用户以为过滤生效，实际没有，PR 上照样一片红，
而且没有任何提示说明「你的 --diff 没生效」。

**修法**：`--scan-only` 也走 `_filter_to_diff`，且退出码按过滤后算。

### bug 2：CI 里 `git diff <base>` 返回空

`collect_diff` 用的是 `git diff <base>`，比的是 **base 与工作树**。

- 本地开发：工作树有未提交改动 → 正常
- CI（PR）：代码已 checkout，**工作树是干净的** → `git diff base` 返回**空**
  → 过滤逻辑认为「没有改动」→ 把所有发现都丢掉 → PR 上永远显示 0 条

**修法**：先判断工作树是否干净。
- 有未提交改动 → 按本地语义（含工作树）
- 干净 → 比 `base..HEAD`

这样两种场景都对，且不需要调用方多传参数。

### bug 3：规则 id 塞在 title 里，SARIF 无法归类

原来是 `title = f"{title}（{rule_id}）"`。信息在，但**不可机读**。

后果：所有发现都归到兜底的 `MARGIN001`，GitHub 上全部显示「未分类」，
无法按规则筛选、无法批量忽略。

**修法**：`Finding` 加独立的 `rule_id` 字段。这个字段还顺便服务了另外两处：
- 跨 Agent 记忆去重（按规则 id 归一）
- 趋势统计（哪条规则命中最多）

### 一处测试数据写错（不是实现问题）

我最初写测试用 `KEY = "sk_live_..."`，期望命中 SEC001，结果 0 命中。
排查发现 SEC001 的判据是「**疑似凭据名** + 字面量」，`KEY` 不在敏感词表里
（`password` / `token` / `api_key` / `secret` …）。改成 `API_KEY` 就对了。

记一笔，免得下次又怀疑是过滤逻辑的问题。

## 六、端到端验证

模拟真实 PR 场景（git 仓库 + 两次提交）：

**场景 1：PR 干净，但仓库里有历史遗留**

```
$ python -m harness -r repo --scan-only --diff HEAD~1 --sarif out.sarif
扫描 3 个文件，命中 1 条：
  [blocker] app/legacy.py:1 SEC001 硬编码密钥

按 --diff HEAD~1 过滤：改动 1 个文件，保留 0 条、省略 1 条改动范围外的历史发现
SARIF 已写入 out.sarif（0 条）
退出码: 0
```

**场景 2：PR 引入了阻断级问题**

```
$ python -m harness -r repo --scan-only --diff HEAD~1 --sarif out.sarif
扫描 3 个文件，命中 2 条：
  [blocker] app/feature.py:2 SEC001 硬编码密钥   ← 本次引入
  [blocker] app/legacy.py:1  SEC001 硬编码密钥   ← 历史遗留

按 --diff HEAD~1 过滤：改动 2 个文件，保留 1 条、省略 1 条改动范围外的历史发现
SARIF 已写入 out.sarif（1 条）
退出码: 1
```

两个场景都正确：**只对「这个 PR 引入了什么」负责。**

## 七、怎么用

### 在别人的仓库启用

1. 复制 `.github/workflows/margin-review.yml` 到目标仓库
2. 配置仓库变量（Settings → Variables）：
   - `LLM_BASE_URL`（例如 `https://api.deepseek.com`）
   - `LLM_MODEL`（例如 `deepseek-chat`）
3. 配置密钥（Settings → Secrets）：`LLM_API_KEY`
4. 开启 Actions 权限：Settings → Actions → Workflow permissions → Read and write

**不配 2、3 也能用** —— 规则扫描照跑，AI 审查跳过。

### 本地模拟 CI

```bash
cd backend
python -m harness -r /path/to/repo \
  --scan-only \
  --diff main \
  --sarif ./out.sarif
echo "退出码: $?"     # 0 无阻断 / 1 有阻断
```

## 八、已知边界（如实说明）

1. **workflow 未经真实 GitHub Actions 运行验证**。YAML 结构、命令、权限配置都做了
   本地核对（`yaml.safe_load` 解析通过、每条命令本地跑通），但 runner 环境
   （Ubuntu / Python 3.12 / `gh` CLI）的差异只能等第一次真实跑才知道。
2. **SARIF 只到行，不到列**。我们本来也只有行号，一致。
3. **不支持跨文件数据流路径**（SARIF 的 code flow）。那需要把数据流建模进 Finding，目前没有。
4. **规模闸门是行数，不是复杂度**。3000 行是个经验值，没有按语言/文件类型细分。
5. **评论不更新，只追加**。同一 PR 多次 push 会留下多条评论。
   行业做法是「sticky comment」（找到上一条编辑它），需要额外调 GitHub API，本次没做。
