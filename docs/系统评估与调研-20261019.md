# Margin 系统完成度评估 + 互联网调研（2026-10-19）

## 一、互联网调研：这个赛道的真实水位（重要，别再用旧印象）

### 商用产品的独立排行（Martian Code Review Bench，16,017 个真实 PR，非厂商自测）

| 工具 | F1 | 精确率 | 召回 |
|---|---|---|---|
| Cubic Dev AI | 65.7% | 72.9% | 59.8% |
| GitHub Copilot | 63.9% | 68.8% | 59.6% |
| Claude | 62.5% | 70.4% | 56.2% |
| Greptile | 61.9% | **80.3%**（最高） | 50.4%（最低） |
| CodeRabbit | 60.8% | 66.8% | 55.8% |
| Qodo | 58.9% | — | — |
| CodeAnt | 50.0% | 72.3% | 38.2% |

**商用产品 F1 天花板 ≈ 66%**，且没有任何一家在独立基准上碾压别人。
厂商自测差距极大（Greptile 自测 82%，Augment 复测同一批 45%）。

### 学术基准（CR-Bench，5,642 个真实 PR 任务）

| 配置 | 精确率 | 召回 | F1 |
|---|---|---|---|
| 单次通过（最强模型） | 0.38 | 0.52 | 0.44 |
| 多次通过 + 过滤 | 0.62 | 0.41 | 0.49 |
| 多智能体共识 | **0.71** | 0.35 | 0.47 |
| **人类基线** | **0.85** | **0.78** | **0.81** |

**核心结论：所有 AI 策略都在一条严格被人类支配的曲线上。**
提高召回 → 精确率必掉到 0.40 以下（60%+ 是误报）。这是市场规律，不是实现缺陷。

### 其他关键事实

- **c-CRAB（新加坡国立大学，234 条人工评论转成可执行测试）**：四个前沿工具
  （Claude Code / Devin / PR-Agent / Codex）**取并集**才通过 41.5%。
  单工具 20–32%。这是"以人类真实评论为金标准"的最严基准。
- **CR-Bench 单模型管线停在 ~60% 精确率**，因为审查者和修复者共享同一个盲区。
- **bounded tool surface（arXiv 2608.09290）**：限制工具返回量 → 精确率 7.23% → 33.90%，
  但召回 28.90% → 20.00%。代价明确。
- **CRJudgeBench**：最强 LLM 判定"不可信评论"只有 **20.77%** 召回 ——
  "看起来专业但其实是错的评论"是全行业未解难题。
- **Spotlight（arXiv 2607.29516）**：定位 Top-K 可疑区域比逐条评论好 3.3 倍、
  省 5 倍 token、快 6 倍。

### 业界公认的关键工程手段（我们缺的）

1. **独立判官层**（CodeRabbit：2-50 个 linter 并行 + 独立 judge 模型逐条打分，无法 grounding 就丢弃）
2. **调用图/仓库索引**（Greptile 预先建全仓语义图）
3. **沙箱执行验证**（Greptile TREX：真的跑起来，日志当证据）
4. **bounded tool output**（每次读取有硬上限，让上下文增长可预测）
5. **reflector 过滤**（只看 diff、只删不加的第二遍）

### 8 个靶场的真实规模（关键发现）

平均 **2 个文件 / 62 行**。s3–s8 全是**单文件 31–44 行**。
`s7-crossfile-flow` 号称"跨文件"，实际只有 3 个文件 / 54 行。

**而 `vulnerable-service`（6 文件 / 231 行 / 23 条标注）明显更接近真实场景，
却没有被纳入 8 个靶场的评估体系。**

### 我独立跑的大样本实测（2026-10-19，deepseek-flash）

用真实模型跑 `vulnerable-service`，同一套自动匹配口径重新评分：

| 容差 | 命中 | 召回 | 精确 | F1 |
|---|---|---|---|---|
| ±0 | 14/23 | 61% | 70% | 65% |
| ±2（BENCHMARK 默认） | 15/23 | 65% | 75% | **70%** |
| ±4 | 16/23 | 70% | 80% | 74% |
| ±6 | 18/23 | 78% | 90% | 84% |

**对比 8 个小靶场：±2 时 F1 82%。真实规模样本掉到 70%（-12pt）。**

### 我自己的一次方法论翻车（记下来防再犯）

先用 ±8 宽容差算出"召回 96% / 精确 110% / F1 102%"—— 精确率超过 100% 就是
**口径在自欺欺人**（同一条发现被反复计入覆盖多条标注）。当即推翻，改报区间。

**教训：任何口径算出的精确率 >100% 或召回 >100%，立刻停手检查分母。**

## 三、能力核对：有 vs 没有

**有（且实现质量不错）**
- 静态前缀 + 动态追加的缓存感知上下文（prefix_fingerprint 可自检），实测 87% 命中
- 熔断（finish 永不熔断、连续语义可恢复）
- `verify_citations`：核对总结引用的文件是否真的读过（但**只核文件、不核行号内容**）
- `cross_check`：规则命中但模型没报 → 标记疑似漏报（确定性规则作交叉验证器）
- 工具渐进披露、四层错误信息、只读助手硬契约（can_edit=False 强制校验）
- 多助手可插拔（AgentSpec 声明式）、工作空间隔离
- 183→184 项回归测试

**没有（与业界差距所在）**
- ❌ **独立判官/误报过滤层**（CodeRabbit 的核心，也是精确率从 0.38→0.62 的关键）
- ❌ **仓库级调用图/符号索引**（只有 read_symbols 列函数名，不是图）
- ❌ **沙箱执行验证**（run_command 被 HighRiskBlocked，所有结论都是静态推断）
- ❌ **bounded tool output**（read_file 有 limit，但无统一硬上限与"截断了多少"的显式告知）
- ❌ **diff 感知的增量审查**（有 git_diff 工具，但没有"只审变更+受影响调用点"的流程）
- ❌ 多语言（read_symbols 仅 Python；样本全是 Python）

## 四、定位结论（诚实版）

**分数对比要小心口径**：我方 82%（小样本自建）、70%（真实规模自建）vs 商用 66%（第三方）。
**不能直接说"我们超过商用产品"**，原因：
1. 样本规模差 100 倍（34 标注 vs 16,017 PR）
2. 任务不同（静态读全仓 vs PR 增量审查）
3. 商用产品面对的是**人类真实会评论什么**，我们面对的是**自己植入的缺陷**
4. c-CRAB 那种最严基准上，前沿工具并集才 41.5%

**可信的结论**：这套系统在"小文件、缺陷明确、单次全读"的场景下，
达到甚至超过商用产品的水平；但这恰恰是**最容易的场景**。
真实规模下（6 文件）已掉 12pt，再放大到 50 文件会掉更多 —— **未测，不敢断言**。

## 五、增强方向（按性价比排序，每项都对应上面的实测缺口）

1. **判官层（最高性价比，2-3 天）**：发现先收集，再由一遍独立 prompt「只核对证据、
   不产生新发现」逐条判 grounded/ungrounded，ungrounded 降级或丢弃。
   预期：精确率 +10~15pt，`verify_citations` 已有基础可直接扩展成「核对行号内容」。
2. **行号引用内容核验（1 天，微创新）**：把 `verify_citations` 从"文件读没读"
   升级为"引用行号的内容与发现描述是否匹配"。业界少见，且直接打 CRJudgeBench 那个痛点。
3. **bounded tool output（1 天）**：所有读取工具统一硬上限 + 显式"已截断 N 行，用 offset 续读"。
   文档说已有，代码里需核实是否统一。
4. **diff 增量审查模式（3-5 天）**：git_diff → 变更行 → 受影响调用点（用 grep 反查），
   只审这部分。这是商用产品的真实工作模式，也是能打出"跨文件"卖点的地方。
5. **更大样本（必须做，否则一切结论不可引用）**：现在平均 62 行太小。
   至少补 3-5 个 500-2000 行的多文件样本。**这是评估可信度的地基。**

# 六、三项「未测」的补测结果（2026-10-19 晚）

## 6.1 m2 / m3 实测

| 样本 | 规模 | 标注 | 报出 | 召回(±2) | 精确(±2) | F1 |
|---|---|---|---|---|---|---|
| m1-order-desk | 14 文件 / 1381 行 | 27 | 23 | 70% | 83% | 76% |
| m2-report-hub | 17 文件 / 1784 行 | 24 | 32 | 75% | 56% | 64% |
| m3-auth-gateway | 15 文件 / 1580 行 | 26 | 26 | 77% | 77% | 77% |
| **平均** | — | 77 | 81 | **74%** | **72%** | **72%** |

**两个大样本的分数都低于小靶场（82%）**，与前面的判断一致：规模放大会掉分。

### 必须记下来的方法论错误（第二次犯）

m2 / m3 首轮算出来的精确率是 **22% / 31%**，看着像系统退化了。逐条读源码核对后发现
**又是标注严重不全**：m2 的 32 条里有 11 条是真缺陷（`get_readonly_replica` 不存在、
`self.save` 不存在、`X-Tenant-Admin` 头被无条件信任……），m3 的 26 条里有 14 条是真的。
补齐后 m2 从 22%→56%，m3 从 31%→77%。

**这是同一个错误犯第二次**（m1 时精确率被算成 30%）。根因是「先写标注、再跑模型」：
标注只能覆盖写的时候想到的缺陷，而模型会找出标注者没想到的。**正确顺序应该是
先跑一遍模型、逐条核实、再定标注**，或者至少要有一轮核对。

### 一个标注错误（m2）

`PY001-a` 原标注写在 `admin_api.py:33`，说是「只看 role=='admin'」，实际缺陷在第 30 行
——「无条件信任客户端自带的 `X-Tenant-Admin` 头」。已修正。这类错会让自动口径
永远匹配不上，属于标注质量问题。

## 6.2 判官层对 s1–s8 的影响

| 指标 | 判官前 | 判官后（初版） | 判官后（加 note 保护） |
|---|---|---|---|
| 平均精确率 | 76% | 76% | **76%** |
| 平均召回 | 86% | **80%**（掉了 6pt） | **86%** |

初版判官在 s5 删了 2 条 note 级发现，召回从 100% 掉到 50%。判断理由：
- `remaining(hits)` 返回 `LIMIT - hits`，判官认为「负数在数学上是对的，不构成缺陷」
- `in_window` 用闭区间，判官认为「这是设计选择，不构成缺陷」

**这两条其实是标注认可的真缺陷**（「边界/前提未被约束」就是 s5 要考的东西）。
所以问题不是判官判错了，而是**判官的口径和标注的口径不一致**。

修法（`judge.py`）：
1. prompt 补一条：note 级要特别保守，只要描述指出的前提确实没校验就 keep；
2. 加一道确定性闸 `_is_fragile_drop`：note 级只有在判官理由里出现
   「没有/不存在/相反/已有」这类**明确反证**词时才允许删，否则保留并计入 `kept_by_guard`。

修后召回回到 86%，精确率不变（本来就没有误报可删）。

**结论：判官对小样本几乎无收益（小样本误报本来就少），主要价值在大样本。
但它会带来召回损失风险，所以 note 级保护是必要的。**

## 6.3 diff 增量审查：完整跑通

构造一次真实改动（在 m1 上新增 `bulk_cancel`，埋了 4 个缺陷），跑 `--diff HEAD`：

- **范围控制正确**：只审了 `app/service.py`，没有把全仓旧问题倒出来
- **6 条发现，全部命中改动**：未定义全局 `WB`、把 order_id 当 SKU 传给 release、
  跳过退款登记、返回值用入参长度、operator 未使用、未加锁
- 3 条 blocker，与埋的缺陷对得上

**顺带抓到一个我自己代码里的真 bug**：`tools_audit.py` 的 `lint_file` 漏了 `import ast`，
一调用就 `NameError`。这不是测试能发现的（没有测试真调 `lint_file`），
是 Agent 在运行时撞到并在总结里如实报告的。已修 + 补回归测试
（`test_lint_file_runs_without_nameerror`）。

**这个 bug 本身是个好证据**：Agent 的「工具失败如实上报」机制真的把问题暴露出来了，
而不是静默吞掉后编个结论。
