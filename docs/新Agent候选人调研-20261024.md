# 新 Agent / 新模块 候选调研 · 2026-10-24

> 目标与上一份不同：**不是把 review / architect 做得更深，而是扩大覆盖面**——
> 再加几个 Agent，让 Margin 从「两个助手」变成「一条研发链路」。
>
> 检索 8 轮、20+ 来源（2026 年 4–10 月）。本文只回答一个问题：
> **哪几个角色值得加，加了之后系统才真正「完备」。**

---

## 一、先量一下接入成本（这决定建议是否可执行）

| 项 | 现状 |
|---|---|
| 加一个 Agent | 写一份 `AgentSpec` + 调一次 `register`（约 80–150 行，含 system prompt） |
| 新产出形态 | 若沿用 `findings` / `blueprint` 则**零成本**；新形态需加一个前端渲染器（约 150–250 行） |
| 已有产出桶 | `finding` / `layer` / `component` / `decision` / `open_question` |
| 已有工具 | 18 个（9 公共 + 4 审查 + 5 架构），新 Agent 可直接复用公共 9 个 |

**结论**：接入新 Agent 的成本很低，**真正的成本在「选对角色」和「写对 system prompt」**。
所以下面按「角色价值」排序，不按「实现难度」。

---

## 二、行业已经把「该有哪些角色」试出来了

Factory（Droid，2026 年 4 月估值 15 亿美元）的产品线基本就是一份标准答案。
它的 10 个 Droid 按职责分工：

| Droid | 干什么 | 关键数字 |
|---|---|---|
| **Review** | 带仓库上下文的审查，能跨多仓对照 | PR→批准周期 −50% |
| **Test** | 给没有覆盖的代码补测试（迁移前先建安全网） | — |
| **Document** | 随 diff 自动更新文档（AutoWiki） | — |
| **Reliability**（原 On-call） | 接 PagerDuty/Datadog/Sentry，定位根因、提修复 | on-call 解决时间 **−96%** |
| Code / Knowledge / Project / Security | 生成 / 知识 / 排期 / STRIDE 安全审查 | — |

另一份分类（CodeRabbit）按「在流程哪个位置出现」划分六类：
IDE / CLI / 后台异步 / **Review** / **Planning** / Slack。

两份分类交叉后，落到本项目能做的，就是下面五个候选。

**关键背景**：这些角色的**共同前提**是「仓库级上下文」。
没有代码图（谁调用谁、哪些测试覆盖它），Test / Document / Reliability 都会退化成瞎猜。
这是为什么本报告把「代码图」列为**所有新 Agent 的前置模块**，而不是一个可选 agent。

## 三、五个候选（按「价值 ÷ 成本」排序）

### 候选 1：策划助手（`planner`）—— 强烈建议

**产出**：结构化实现计划（步骤 + 每步验收条件 + 涉及文件 + 风险点）

**为什么排第一**

- **它填的是整条链路的第一个空位。** 现在的链路是「审查现有代码」「设计架构」——
  都是**看现状**。缺的是「要做一个改动，该怎么落地」。
  这是研发流程里**最高频**的入口，也是 Planning Agent 被单列为一类的原因。
- **成本最低。** 产出形态可以直接复用 `blueprint` 的「分层/组件/决策/开放问题」结构，
  或新增一个 `plan` 桶（步骤列表），前端渲染器与现有发现列表同构。**零新工具**。
- **它天然衔接现有两个 Agent**：
  `planner` 出计划 → `review` 审「这个计划有没有遗漏」→ 落地后 `review` 再审代码。
  这让「多个 Agent 协作」有了具体叙事，而不只是并列摆着。
- **行业证据**：Planning Agent 的输入是 ticket / PRD / 设计文档，输出是「agent-ready prompt」
  与实现计划；它在多 Agent 系统里通常就是**协调层**。

**system prompt 该强调什么**（照着写）

- 必须给**验收条件**（什么叫做完了），否则计划无法验证
- 必须标**风险点**与「哪一步可能推翻前面的假设」
- 不许写「优化代码质量」这类无法验收的步骤
- 每步要指到**具体文件/模块**，指不到就说明为什么指不到

**成本**：低（~150 行 spec + prompt + 一个渲染器）

---

### 候选 2：测试助手（`tester`）—— 强烈建议

**产出**：测试用例清单（含「这条测试在什么情况下会失败」）+ 可选的实际测试文件

**为什么值得单独做一个 Agent**

- **行业共识：测试生成是 ROI 最高的起点。** 多份材料一致：
  「测试是定义良好、可重复、可验证的——agent 自主性的理想条件」，
  「从测试生成切入的团队看到最快的 ROI，几周内覆盖率翻倍」。
- **它和 `review` 是互补而非重复**：`review` 找「代码错在哪」，`tester` 找「哪段代码没被验证」。
  缺陷视角与覆盖视角，是两件不同的事。
- **它能反过来喂 `review`**：新写的测试让「修复是否真的修好」第一次可验证。
  这是把项目从「只能报告问题」推进到「能证明问题已解决」的关键一环。
- **已有基础**：`run_tests` 工具已存在，`suffixes` 已按语言过滤。改动集中在 prompt 与产出。

**最有价值的一个变体：特征测试（characterization test）**

这是本次调研里**最反直觉、也最实用**的发现：

> 不要写「代码应该怎样」的测试，要写「代码现在实际怎样」的测试——
> **包括那些看起来是错的行为**。它的价值在于把不可触碰的系统变成可以改的系统，
> 而且它的正确性**可以机械验证**（跑一遍现有系统就知道对不对）。

对老旧/无测试仓库，这比「补单元测试」有用得多，而且和 `review` 天然配合：
`review` 说「这里行为可疑」→ `tester` 把这个行为**钉成一条测试**→
将来谁改坏了，测试会立刻报。这是一条完整的证据链。

**关键警告（必须写进 prompt）**

- 不许生成「断言当前错误行为是对的」的测试（测试会在有 bug 的代码上通过，等于固化缺陷）
- 边界条件、负例、并发/失败路径优先于 happy path
- 无法从仓库证据推断预期行为时，**标为「待确认」而不是编一个断言**

**成本**：低→中（~200 行 spec + prompt；`run_tests` 已有）

### 候选 3：仓库导读助手（`guide` / onboarding）—— 建议

**产出**：一条「从这里开始读」的路径 + 关键模块说明 + 首个可改动的点

**为什么建议**

- **它是「解释类回答」里唯一有明确产品形态的。** 调研里最具体的参照是 RepoGuide：
  架构浏览 → 推荐「先读这些文件」→ 跑起来的步骤 → 有证据的 Q&A → **第一个贡献点**。
- **对答辩极友好**：评审第一件事就是「打开这个项目看不懂」。这个 Agent 正好解决它。
  可以拿本项目自己当靶场：让 `guide` 解释 Margin，输出直接当文档用。
- **和 `architect` 的区别要写清**（否则会被认为重复）：
  `architect` 产出「应该怎么设计」的方案；`guide` 产出「现在实际是怎么组织的」的导读。
  **A 不等于 B**：一个是 proposals，一个是 current-state explanation。
- **行业证据**：Cursor 创始人说，进入陌生代码库时用得最多的就是 Q&A 与搜索；
  研究侧（RepoAgent, EMNLP 2024）也把仓库级理解列为「人与 agent 共同的首要瓶颈」。

**system prompt 关键约束**

- **每个结论必须给文件+行号引用**，否则会编。这一条能直接压掉大部分幻觉。
- 必须区分「代码里能读到的」与「需要问人的」（历史原因、约定俗成）
- 不许给「这个模块大概负责用户相关逻辑」这种不可验证的概述

**成本**：低（~150 行 spec + prompt；产出可复用 blueprint 的分层结构，改语义即可）

### 候选 4：缺陷复现 / 事故定位助手（`repro` / `triage`）—— 谨慎建议

**产出**：复现步骤 + 故障根因假设 + 最小修复建议（**只报告，不改代码**）

**为什么值得考虑**

- 它是 Factory 报告里「意外地最受欢迎」的角色（on-call 解决时间 −96%）。
  说明真实团队的痛点在**定位**而不是**生成**。
- 与 `review` 的区别：`review` 是「静态读代码找潜在缺陷」；
  `triage` 是「从现象（报错/日志/追踪）倒推根因」。**前者是预防，后者是急救。**
- 有一个极强的具体做法值得抄：**把生产故障转成回归测试**——
  从 trace 里取出失败的 span、异常、下游响应、**部署的 commit**，
  再生成一条「在修复前失败、修复后通过」的确定性测试。
  调研里明确写了这条约束：「不要断言观察到的 bug 是正确的行为」——
  否则测试会在有 bug 的代码上通过，把缺陷固化下来。

**为什么只说「谨慎」**

- 需要**外部输入**（日志/追踪/工单）。本项目目前没有这类数据源，
  要么接 MCP（PagerDuty / Sentry），要么让用户手工粘贴——后者体验很差。
- **行业一致警告：可以做定位，不可以做自动处置。**
  「一个读了监控数据就决定重启服务的 agent 是负债而不是资产」。
  失败模式是灾难性的（重启错服务、漏掉级联依赖、在发布窗口重启）。

**若做，边界必须写死**：只读、只报告、`can_edit=False`、
不接任何「重启/回滚/改配置」类工具。这正好复用架构助手已有的只读硬契约。

**成本**：中（需要定义输入格式 + 新产出形态 + 严格护栏）

---

### 候选 5：文档同步助手（`scribe`）—— 可选

**产出**：随 diff 更新的文档补丁（README / API 参考 / 架构文档 / 运行手册）

**为什么可选而不是建议**

- 它确实是个真实痛点（「文档是没有即时交付物所以永远排在最后的事项」），
  也是 Factory Document Droid 的定位。
- **但对本项目收益有限**：本项目文档已经相当完整（README 184 行、
  5 份 docs、BENCHMARK、CONTRIBUTING）。再加一个「写文档的 agent」边际价值低。
- 它和 `architect` 的边界也容易糊（都在讲架构）。

**如果要做，选最窄的切口**：只做「**代码改了但文档没跟上**」的检测与补丁，
不做「从零生成文档」。前者有客观判定标准（drift detection），后者无法验收。

**成本**：低（但价值也低）

## 四、除了 Agent，还该加的两个「模块」

这两个不是 agent，但**决定了上面哪些 agent 能不能成立**。

### 模块 A：仓库代码图（`codegraph`）—— 所有新 Agent 的前置

**为什么必须先做**

Test / Guide / Triage 三类 agent 都依赖同一个东西：**谁调用谁、哪些测试覆盖它、改动波及哪里**。
没有它，这三个 agent 都会退化成「grep + 猜」。

**最小可落版本**（不引向量库，保持零依赖定位）

用 `ast`（Python 内置）或可选 tree-sitter，抽符号与边：`DEFINES` / `CALLS` / `IMPORTS` / `TESTED_BY`，
存 SQLite。对外只暴露 4 个查询：

| 查询 | 谁在用 |
|---|---|
| `who_calls(symbol)` | review / triage |
| `impact(symbol)` | review / planner |
| `tests_for(symbol)` | tester / review |
| `detect_changes(diff)` | planner / triage |

**行业参照**：GitNexus 的 `impact` 用「深度环」表达波及范围（d=1 必坏 / d=2 可能受影响 / d=3 需测试），
这个表达法比「列出所有相关文件」有用得多，建议直接抄。

**成本**：中大（800–1200 行），但它是**一次投入、三个 agent 受益**。

### 模块 B：跨 Agent 的记忆/知识沉淀 —— 让「多个 Agent」真正成立

现在每个运行是独立的。加了 4 个 agent 之后会出现新问题：**它们互相不知道对方发现了什么**。

最小做法：把每个 run 的产出（发现 / 计划 / 测试清单）按仓库聚合成一份
「这个仓库的已知情况」，作为后续运行的上下文注入。

**为什么重要**：调研里明确指出的核心区别是——
「现在的 review 工具没有记忆，每次审查都独立，你无法看出代码库在变好还是变坏」。
这一条正好能变成一个新的可报告指标：**同一仓库多次运行的缺陷趋势**。

**成本**：中（~300 行 + 前端一个趋势视图）

## 五、排期建议

```
第 0 步（前置）
  模块 A 代码图            ← Test/Guide/Triage 的地基，先做

第 1 批（低成本高价值，可并行）
  候选 1 planner           ← 填链路第一个空位，零新工具
  候选 2 tester            ← 复用 run_tests，ROI 最高的角色

第 2 批
  候选 3 guide             ← 可拿本项目当靶场，答辩友好

第 3 批（视精力）
  模块 B 跨 Agent 记忆      ← 让「多个 Agent」从并列变成协作
  候选 4 triage            ← 需要外部数据源，边界要写死

可选
  候选 5 scribe            ← 本项目文档已完整，边际价值低
```

**如果只能加一个**：选 `tester`。理由：它复用已有工具、ROI 在行业里被反复验证、
并且它补的是「证明修好了」这个当前系统完全缺失的能力。

**如果能加两个**：`planner` + `tester`。这两个加起来构成
「**计划 → 实现 → 验证**」的最小闭环，叙事完整度会有质的变化。

## 六、一个必须避开的认知陷阱

调研里反复出现同一个警告，值得单独写出来：

> **66% 的开发者说，AI 给出的「几乎对了但不对」的方案是他们最大的挫败来源，
> 而 debug 这些近失方案比自己写还慢。**

这意味着：**加 Agent 不等于加价值**。一个「看起来能干活、实际产出半对」的 agent，
对用户的伤害大于没有它。

所以对每个新 Agent，判断标准不该是「它能不能跑通」，
而该是「**它的产出有没有一个机械可验证的判定**」：

| Agent | 可机械验证吗 |
|---|---|
| `tester` | ✅ 生成的测试跑一遍就知道对错 |
| `planner` | ⚠️ 部分（步骤能否指到真实文件/函数可验证） |
| `guide` | ⚠️ 部分（引用能否回读到真实代码可验证） |
| `triage` | ❌ 根因是假设，只能靠人判定 |
| `scribe` | ⚠️ 部分（补丁能否编译/文档是否漂移） |

**这条应当直接进项目的评审纪律**：新 Agent 的产出必须挂上一个可验证信号，
否则只是把不确定性搬了个位置。
