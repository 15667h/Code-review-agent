# 项目定位对标分析 · 2026-10-25

> 回答两个问题：**我们对标什么产品？** 以及 **基于这个定位，还该加什么 Agent？**
> 检索 4 轮，来源均为 2026 年 5–10 月材料。

---

## 一、结论先说

**我们不是 Claude Code，是「独立验证层」（Independent Verification Layer）。**

用行业在 2026 年已经明确的一句话概括：

> **写代码的 Agent 不该给自己的代码签字。**

GitHub、Qodo、CodeRabbit 三方在 2026 年得出同一个判断，Gartner 也把它写成了品类。
我们所在的位置，是**代码生成之外的第二个系统**。

---

## 二、两种产品的分界线在哪

行业现在的分法是**按「PR 的哪一侧」**：

| | Coding Agent | Code Review Agent（我们这一类） |
|---|---|---|
| 代表 | Claude Code、Cursor、Codex CLI、Devin | Qodo、CodeRabbit、Greptile、SonarQube |
| 在 PR 的哪一侧 | **写**（产出 diff） | **审**（评估 diff） |
| 核心能力 | 改文件、跑命令、迭代到测试通过 | 全仓上下文、跨文件影响、规则一致性 |
| 成功标准 | 代码能跑 | **这个改动该不该合并** |
| 失败模式 | 写错代码 | **漏审**（比写错更危险，因为没人兜底） |

**为什么这个分界线重要**（这是本次调研最有价值的一条）：

> 同一个模型既写又审，会让漏洞在**迭代中放大**：一项对照研究发现，
> 模型反复自我修正、没有外部检查时，**关键漏洞在 5 轮内增加超过三分之一**。
> 另一项研究：同一模型家族生成的代码，被同家族模型测试时通过率
> **高出 9–17 个百分点**。它们共享盲点。

这就是为什么 Gartner 在 2026 年 6 月的报告里明确说：

> 「coding agents 是最成熟的一类，作为第一遍筛查有真实价值……
> 但**不该取代生命周期正式节点上的权威评审与测试**：PR 时的代码审查、
> 专门 QA 周期里的测试。**专门构建的 agent 在这些专门职能上表现更好。**」
>
> —— *Don't Use AI Coding Agents for Every Software Engineering Task*, 2026-06-02

**Gartner 已经把 "Code Review Agent" 列为 Software Engineering Agents 下的一个独立品类**，
Qodo 是其中的示例厂商。所以这不是我们自封的定位，是行业已有的格子。

## 三、我们的实际位置（自查，不美化）

| 维度 | 我们的现状 | 对标产品的做法 | 差距 |
|---|---|---|---|
| **写代码能力** | 有 `apply_patch`，但**只有 review 拿到**，且不主动改 | Claude Code 的核心就是改代码 | 我们**不该**补这个 |
| **全仓上下文** | ✅ codegraph：符号图 + 调用边 + 影响环 | Greptile 全仓索引、Qodo 跨仓 | 我们**只 Python 深层** |
| **多语言** | 15 种语言，但只有 Python 是 deep | SonarQube 30+ 语言、DeepSource 30+ | 差距明显，但诚实分级了 |
| **规则一致性** | ✅ 14 条确定性规则，6 条跨语言 | Qodo「Living Rules」、SonarQube Quality Profile | 我们**没有团队自定义规则** |
| **PR / CI 集成** | ❌ 完全没有 `.github/` | 所有对标产品都跑在 PR 上 | **最大缺口** |
| **治理与可追溯** | ⚠️ 有 run 归档与证据，但没有规则命中趋势 | Qodo 治理面板、SonarQube Quality Gate | 中等缺口 |
| **独立验证** | ✅ 判官层 + 四 Agent 分离 | 行业共识方向 | **我们的优势** |
| **可插拔 Agent** | ✅ `AgentSpec` 声明式 | 少见（Qodo 是多 agent 但封闭） | **差异化亮点** |

**一句话**：我们在「独立验证」这条主线上是对的，但**缺了「跑在 PR 上」这个落地形态**——
现在只能本地手动跑，不是工程流程的一部分。

---

## 四、那我们该不该加「写代码」的 Agent？

**不该。而且这是本次调研最重要的判断。**

三个理由：

**1. 定位自毁。** 我们的全部价值建立在「写与审分离」上。
加一个会改代码的 Agent，等于自己把这条线抹掉——评审会立刻问：
「那你和你审的代码是同一个系统吗？」

**2. 我们打不过。** Claude Code / Cursor / Codex 是几十亿美元堆出来的产品。
在这个方向上做第五名，等于放弃我们唯一的结构性优势。

**3. 行业正在往反方向走。** 2026 年的趋势是**分离更彻底**，不是合并：
CodeRabbit 明确说「平台无关、独立于 coding agent 运行」；
mabl 拿「the agent that writes the code can't be the one that signs off on it」
当产品主张，并因此进了 Gartner MQ。

**唯一例外**：如果做「修复建议」（输出 patch 但**不自动应用**，由人决定）。
这在定位上仍然是「验证层给出可执行的结论」，不越界。但优先级低。

## 五、基于这个定位，该加什么 Agent

判断标准不是「能不能做」，而是**「这个角色是不是验证层的一部分」**。

### 强烈建议加（补验证层的完整性）

#### 1. `hunter` 逻辑级安全审计 —— 最该加的一个

**为什么**：现有 `review` 找的是通用缺陷，`SEC00x` 规则找的是**模式级**问题
（硬编码密钥、`eval`、命令注入）。但真正危险的是**逻辑级**漏洞：
越权、IDOR、状态机绕过、竞态——这些**规则写不出来，只有推理能发现**。

SonarQube 专门为此做了 Hunter Agent，理由是「需要超越模式匹配的推理」。
我们的靶场 `m1-order-desk` 里就有一堆这类缺陷
（`has_permission_to_view` 恒返回 True、已付订单取消跳过退款分支）。

**产出**：`threat`（威胁模型 + 具体攻击路径 + 受影响端点）
**与 review 的边界**：review 找「这里会崩」，hunter 找「这里能被越权」。
**成本**：中（新增一个 agent + 威胁建模 prompt + 攻击路径验证）

#### 2. `verify` 独立复核 / 对抗反驳 —— 已经调研过，性价比最高

**为什么**：这是「独立验证层」最纯粹的形态。
判官层现在是「一个复核者看一遍」，行业 2026 年的做法是
**派 2–3 个专门唱反调的 agent 去证伪每条发现**，只有活下来的才展示。

调研原文：现在这代 harness 幻觉更少，不是模型更强，而是
「一个似是而非的发现，在到你眼前之前已经被三个被要求证伪它的 agent 杀掉了」。

**产出**：不改产出，而是**过滤已有产出**（降低误报、给每条发现一个「存活置信度」）
**成本**：低（200–300 行）
**额外价值**：能直接产出一个可报告的实验——「加 refuter 前后精确率变化多少」

#### 3. `guide` 仓库导读 —— 答辩友好且补流程起点

**为什么**：验证层要落地，第一道坎是「看不懂这个仓库」。
Cursor 创始人说进入陌生代码库时用得最多的就是 Q&A 与搜索。

**产出**：`reading_path`（从哪读起 + 关键模块 + 首个可改动的点）
**与 architect 的边界**：architect 是「应该怎么设计」，guide 是「现在实际怎么组织」
**成本**：低
**额外价值**：可以拿本项目自己当靶场，输出直接当文档用

### 可以考虑（但优先级低于上面三个）

| Agent | 为什么排后面 |
|---|---|
| `scribe` 文档漂移检测 | 本项目文档已很完整，边际价值低；且容易和 architect 糊 |
| `triage` 事故定位 | 需要外部日志源（PagerDuty/Sentry），**行业共识：可定位不可处置** |
| `fixer` 修复建议 | 越界风险高（见第四节），且价值不如前三者 |

### 明确不该加

| 想法 | 为什么不该 |
|---|---|
| `coder` 写代码 agent | 定位自毁 + 打不过 + 行业反方向 |
| `refactor` 重构 agent | 同上，且与 planner 重叠 |
| 更多「看现状」的 agent | review / architect / guide 已覆盖 |

## 六、但比加 Agent 更紧急的一件事

**我们没有 `.github/`，也就是没有 PR 集成。**

所有对标产品（Qodo / CodeRabbit / Greptile / Copilot / Sonar）都是**跑在 PR 上**的。
我们现在只能本地手动跑——这意味着：

- 评审问「这东西怎么用」，我们只能演示本地命令行
- 「独立验证层」的价值在**流程节点**上，不在本地工具上
- 没有 PR 集成，就没有「每次提交都过一遍」的持续性

**建议顺序**：先补 CI 集成（约 200 行 YAML + 一个 CLI 入口），
再加 `hunter`。因为 CI 是「让验证层真的在验证层的位置上」，属于定位落地；
加 Agent 属于能力扩展。

## 七、对标产品速查表（用于答辩时的一句话对应）

| 我们 | 对标 | 我们的差异 |
|---|---|---|
| `review` | CodeRabbit 主力审查 | 我们给每条发现**证据 + 置信度分级**，不给风格意见 |
| `hunter`（待建） | SonarQube Hunter Agent | 同样针对逻辑级漏洞；我们更轻、可插拔 |
| codegraph | Greptile 全仓索引 / GitNexus | 我们零依赖、SQLite、边分 EXTRACTED/INFERRED |
| 判官层 + `verify`（待建） | Qodo 多 agent 复核 | 我们可复现地报告「加复核前后精确率」 |
| `tester` | Qodo Cover（测试生成） | 我们强调**特征测试**（锁当前行为）与**验证状态三态** |
| `planner` | Qodo PR-Agent `/describe` | 我们从**可验收性**出发，每步 `done_when` 必填 |
| `architect` | 少见（多数产品不做架构） | **差异化**：分层图 + 决策 + 开放问题 |
| `AgentSpec` 可插拔 | — | **差异化**：加 Agent 不改既有代码 |
| — | SonarQube Quality Gate | **我们缺**：可强制的合并门禁 |
