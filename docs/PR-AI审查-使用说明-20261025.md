# 怎么用 PR 的 AI 审查

> 分三件事：**启用**（一次性）、**触发**（每次）、**看结果**（怎么读）。

---

## 一、启用（一次性，约 2 分钟）

### 1. 配 API Key

仓库页 → **Settings** → 左侧 **Secrets and variables** → **Actions**

点 **New repository secret**：

| 字段 | 值 |
|---|---|
| Name | `LLM_API_KEY` |
| Secret | 你的 key（例如 `sk-...`） |

点 **Add secret**。

**这一步不做会怎样**：规则扫描照常跑，AI 审查段落自动跳过，
PR 评论里会写一句「AI 审查未运行：未配置 LLM_API_KEY」。
**不会让 PR 变红** —— 这是刻意的：开源项目的 fork PR 拿不到 secrets，
如果这里硬失败，所有外部贡献都会被一个「配置缺失」卡住。

### 2. （可选）换模型或端点

同一个页面切到 **Variables** 标签，加两个变量即可覆盖默认值：

| Name | 默认值 | 说明 |
|---|---|---|
| `LLM_BASE_URL` | `https://api.deepseek.com` | OpenAI 兼容端点 |
| `LLM_MODEL` | `deepseek-flash` | 模型名 |

**不配就用默认值。** 换自建 vLLM / 别的厂商时才需要改这两个。

### 3. 确认 Actions 有写权限

**Settings** → **Actions** → **General** → 拉到底 **Workflow permissions**

选 **Read and write permissions**。（审查要发 PR 评论、要上传 SARIF，
只读权限会导致评论发不出去、Security 页空的。）

### 4. 确认 workflow 文件存在

```
.github/workflows/margin-review.yml
```

如果是往**别的仓库**接入，把这个文件复制过去即可，
但需要那个仓库里也有 `backend/` 目录（本项目的代码）。

## 二、触发（每次）

### 方式 1：开 / 更新 PR（自动）

workflow 监听三种事件：

```yaml
on:
  pull_request:
    types: [opened, synchronize, reopened]
```

- **opened**：新建 PR
- **synchronize**：往 PR 分支推了新提交
- **reopened**：重新打开

**只要往 PR 分支 push，就会自动重跑**，不用手动点。

### 方式 2：手动触发（对任意分支跑一次）

仓库页 → **Actions** → 左侧 **Margin 代码审查** → 右侧 **Run workflow**

- 选分支
- `base` 留空 = 对比 PR base；填 `main` 之类 = 对比该 ref

### 方式 3：本地跑（不经过 GitHub，最省事）

调试 prompt 或看细节时用这个，不用等 runner：

```bash
cd backend
export LLM_API_KEY="sk-..."
export LLM_BASE_URL="https://api.deepseek.com"
export LLM_MODEL="deepseek-flash"

# 只看规则扫描（不调模型，秒级）
python -m harness -r .. --scan-only --diff main

# 带 AI 审查
python -m harness -r .. --diff main \
  -g "审查本次 PR 的改动，只关注会导致错误行为、安全问题、资源泄漏的实现。如果没有值得修的实质问题，就直接说没有。"
```

**`--diff main` 是关键参数**：只审改动范围，不审全仓历史遗留。

## 三、看结果（三个地方）

### 1. PR 评论（最直接）

workflow 会在 PR 里发**一条**评论，内容分两块：

```
### Margin 审查结果
改动规模：26 行。详情见 Security → Code scanning。

▶ 确定性规则扫描        ← 折叠块，点开看
▶ AI 审查              ← 折叠块，点开看
```

没有 AI 审查时会显示：「AI 审查未运行：未配置 LLM_API_KEY」。

### 2. Security → Code scanning（可筛选、可标记误报）

仓库页 → **Security** 标签 → **Code scanning**

两个 category：

| category | 来源 |
|---|---|
| `margin-rules` | 确定性规则（秒级，不需要模型） |
| `margin-ai` | AI 审查（需要 key） |

这里的价值是**能操作**：
- 按规则筛选（只看 `SEC001`）
- 标记误报（之后相同指纹不会再报）
- 修复后自动消失（靠指纹匹配）

### 3. Actions 日志（出问题时看）

仓库页 → **Actions** → 点具体运行 → 点 **review** job

日志是分步的，**哪一步红了就看哪一步**：

| 失败的步骤 | 大概率原因 |
|---|---|
| 安装依赖 | `requirements.txt` 或 Python 版本 |
| 规则扫描 | 扫描本身报错（看日志里的 traceback） |
| 上传 SARIF | 权限不足，或 SARIF 格式被服务端拒 |
| AI 审查 | key 无效 / 端点不通 / 模型名错 |
| 发评论 | `pull-requests: write` 没生效 |

**注意**：AI 审查那一步是 `continue-on-error: true`，
即使它失败，整个 job 也不算失败 —— 你要主动去日志里看它有没有跑成。
这样设计是为了「审查不阻塞合并」，但代价是失败会被吞掉。

## 四、几个常见问题

### Q：为什么我的 PR 显示 0 条发现？

按可能性排序：

1. **本次改动确实没有引入问题** —— 这是正常的，
   历史遗留不会被报（`--diff` 只比改动范围）。
2. **改动全在测试文件里** —— `_is_test_file` 会豁免测试文件，
   夹具里的假凭据不该按生产标准报。
3. **改动规模超过 3000 行** —— workflow 会跳过审查并提示拆分。
   门槛不是为省钱，是模型对超大 diff 会「跳读」但输出看起来依然完整。

### Q：AI 审查要多久？

本地实测（`deepseek-flash`，一个 26 行的改动）：**40–90 秒**。
CI 里加上 checkout 与依赖安装，整体约 2 分钟。
`--max-iterations 30` 是上限，实际用不到。

### Q：能只跑规则、不花 token 吗？

能。规则扫描那一层**永远跑**，且不需要 key。
AI 审查是附加层 —— 不配 key 就只有规则层，成本为零。

### Q：抓到的问题会自动修吗？

**不会，而且是刻意的。** 这个项目的定位是「独立验证层」——
写代码的 Agent 不该给自己的代码签字。它只报告，改由人或别的工具做。
报告里每条都有行号与证据，可以直接拿去改。

### Q：私有仓库能用吗？

能，但要注意：GitHub Actions 的 minutes 会计费（私有仓库）。
另外 `LLM_API_KEY` 会出现在 runner 环境里，**不要**在 PR 里打印它
（workflow 里也没有 echo）。

---

## 五、一句话总结

**配一个 secret（`LLM_API_KEY`）→ 开 PR → 看 PR 评论和 Security 页。**

规则层始终在跑；AI 层有 key 才跑，没 key 不影响 PR 合入。
