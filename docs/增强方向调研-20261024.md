# Margin 增强方向调研 · 2026-10-24

> 全网大规模检索（8 轮、20+ 来源，全部为 2026 年 4–10 月材料）。
> 目的不是罗列趋势，而是回答一个问题：**以本项目的现状，加什么最值。**
> 每一项都标注了「现状缺口」「行业做法」「工作量」，可据此直接排期。

## 一、先说结论

现在项目**不缺「单点能力」，缺「闭环」**。

已具备的骨架比想象中完整：

| 能力 | 现状 |
|---|---|
| 增量 diff 审查 | ✅ `diffmode.py`（只审改动行 + 受影响调用点） |
| 判官复核 | ✅ `judge.py`（独立复核、剔除撑不住证据的发现） |
| 工具调用闭环 | ✅ 18 个工具（9 公共 + 4 审查 + 5 架构），含 `run_tests` / `lint_file` / `apply_patch` |
| 预算与护栏 | ✅ `budget.py` / `pacing.py` / `guardrails.py`（477 行）/ `sandbox.py` |
| 架构速写与评分 | ✅ `sketch.py` / `arch_score.py`（对标学术指标） |
| 可插拔 Agent | ✅ `AgentSpec` 声明式注册 |
| 双层评测 | ✅ 8 靶场 / 34 标注 / 双口径报告 |

**真正的缺口是这四条**（下面第二节展开）：

1. **没有验证闭环**——能改代码、能跑测试，但两者没连成「改 → 跑 → 不过就重来」的循环
2. **没有仓库级结构索引**——只有 `grep` + `read_symbols`（单文件 AST），跨文件依赖靠模型自己猜
3. **只支持 Python**——规则 10 条（ERR001-2 / PY001-3 / RES001-2 / SEC001-3）全部 `suffixes=(".py",)`，换个语言直接失效
4. **没有 CI / PR 集成**——只能本地手动跑，不是「开发流程的一部分」

行业在 2026 年已经把这四条当作及格线（见第三节证据）。补齐这四条，项目才从
「一个能跑的 demo」变成「一个能装进团队流程的工具」。

## 二、六个增强方向（按性价比排序）

性价比 = 对赛题评分的影响 ÷ 实现与验证成本。
排序依据：赛题里 AI 技术深度占 35%，所以**能证明「这套架构确实更强」的能力优先**。

### 方向 1：验证闭环（最高优先级）

**缺什么。** 现在 `apply_patch` 能改文件、`run_tests` 能跑测试，但**没有任何东西把它们串成环**。
模型改了代码之后，没有任何机制强制它证明「改对了」。

**行业做法（2026 主流）。** 顶级 Agent 的共同特征不是「生成能力强」，而是**被逼着用真实测试结果证明变更有效**：

- **分级证据闸门（Staged Evidence Gates）**：按成本递增排序，便宜的先跑。
  编译/语法闸门 → 目标测试闸门 → 全量回归闸门。
  EviACT 报告这套排序带来 1.6–6.0pt 的解决率提升，API 成本降 70–88%。
- **Bug 判别性验证（BSG-VA）**：一条测试通过**只有在原始缺陷代码上会失败**时才算证据。
  实测 3730 次验证事件里，46% 的「阳性证据」是回归性通过或误导性的，对定位缺陷毫无信息量。
  做法：把测试补丁回放到三个状态 —— 原始 buggy 代码（B）、候选补丁（S）、人工金标准修复（G）。
  只有 **B 失败 + G 通过** 才算「金标准对齐的缺陷判别证据」。
- **范围约束**：补丁必须最小、不许改测试、不许越出白名单路径。
  用 `git diff --name-only` + allowlist 校验，测试被改动直接判失败。

**怎么做（与本项目契合的落法）。**

新增一个 `harness/repair.py`，把现有零件串起来：

```
record_finding（已定位）
  → propose_patch（apply_patch，最小补丁）
  → syntax_gate（ast.parse / 便宜，毫秒级）
  → target_test_gate（run_tests -k <相关测试>）
  → bug_discriminating_check（把测试回放到 fix 前的代码上，必须失败）
  → full_regression（run_tests 全量或受影响子集）
  → 产出「证据包」：根因 + 补丁 + 改动文件 + 各层闸门结果
```

关键设计：**这个环必须由确定性代码驱动，不是让模型自己判断要不要跑测试**。
模型只会说「我已检查」，那是无效证据。

**为什么值。** 这是 2026 年这个赛道**最核心的差异化**。访谈里最尖锐的一句：
「2026 年 Coding Agent 的竞争焦点已经从生成能力转移到验证能力」。
而且它能把现有测试直接复用 —— 项目已经有 283 个测试和 8 个靶场，天然是验证素材。

**工作量**：中（约 600–800 行 + 测试）。风险低，因为零件都在。

### 方向 2：仓库级结构索引（代码图）

**缺什么。** 现在只有 `grep`（正则文本）和 `read_symbols`（**单文件** AST）。
跨文件的「谁调用了我」完全靠模型自己 grep 猜。实测后果：改了一个函数签名，
三个调用点会坏，但审查器从来没读过那三个文件。

**行业做法。** 2026 年这一类工具全部收敛到「代码是图，不是文本」：

- 用 tree-sitter 把每个文件解析成 AST，抽出符号（函数/类/方法/模块）与关系
  （`DEFINES` / `CALLS` / `IMPORTS` / `INHERITS_FROM` / `TESTED_BY`）
- 存进图（SQLite 就够，不必上 Neo4j），节点只存 span（file/start/end），正文按需读盘
- 检索两步走：语义/关键词找入口 → **沿图向外遍历**（callers / callees / 类型定义 / 测试）
- 增量更新：只重解析改动的文件，秒级
- 与向量索引分开存、用节点 ID 关联（不要试图把结构塞进向量 metadata）

参照实现：GitNexus（`context` / `impact` / `trace` / `detect_changes` 等 17 个工具）、
Codebase-Memory（SQLite + 14 个 MCP 工具，报告 token 成本降 10×）、
Code-Graph-RAG（Memgraph + 统一跨语言 schema）。

**怎么做。** 直接对应本项目的最小可落版本：

新增 `harness/codegraph.py`（纯标准库 + 可选 tree-sitter）：

| 工具 | 语义 | 对应的现有痛点 |
|---|---|---|
| `who_calls(symbol)` | 谁调用了这个函数 | 改签名时不知道会坏哪 |
| `impact(symbol, depth=2)` | 影响半径，d=1 必坏 / d=2 可能受影响 / d=3 需测试 | 评审时给不出「波及范围」 |
| `trace(a, b)` | 两个符号间的最短调用链 | 审查跨文件数据流时靠猜 |
| `tests_for(symbol)` | 哪些测试覆盖它 | 修复后不知道跑哪个测试 |
| `detect_changes` | 把当前 diff 映射到受影响的执行流 | 增量审查的入口 |

**为什么不直接上 embedding。** 加向量库会破坏项目「零依赖、可审计」的定位。
先做**纯结构图**（AST + 调用/导入边），用不上就把成本降到最低；语义检索作为可选增强。

**工作量**：中大（800–1200 行）。但它是方向 1 的前置 —— 没有 `tests_for`，
修复环就不知道跑哪个测试。

### 方向 3：多语言支持

**缺什么。** 规则集 10 条全部 `suffixes=(".py",)`，`scan_tree` 默认也只扫 `.py`。
换句话说：**这个审查器对非 Python 仓库完全失明**。

**行业做法。** tree-sitter 覆盖 66+ 语言；`ast-grep` 用 YAML 声明式规则，
一种语言接入只需一个 YAML 模式文件（Ruby 就是这样接进去的）。
规则写成「AST 模式」而不是「正则」，能消掉注释/字符串里的假阳性。

**怎么做（分两步，不必一步到位）。**

1. **低成本过渡**：把 `Rule.suffixes` 变成可配置，规则按语言分组；
   先用**语言无关的正则规则**（危险 API 调用、硬编码密钥、`eval`/`exec` 类）
   覆盖 JS/TS/Java/Go，保守但能用。**不追求深度，先消除「完全失明」。**
2. **正解**：接 `ast-grep`（Rust 单二进制，`pip install ast-grep-cli`，可作为可选依赖）。
   规则用 YAML 写，`sg scan --format sarif` 直接出 SARIF 报告，顺带解决方向 6 的产物格式。

**关键取舍**：不要把「支持多语言」理解成「每种语言都要写深度规则」。
诚实做法是——非 Python 语言只承诺「结构性缺陷的粗筛」，并**在报告里明确标注置信度差异**，
而不是假装同等能力。这与项目「诚实标注」的既有纪律一致。

**工作量**：小→中。第一步（配置化 + 通用规则）约 200 行；第二步接 ast-grep 约 300 行。

### 方向 4：对抗性复核（Adversarial Refutation）

**缺什么。** 现在有 `judge.py` 做独立复核，但那是「一个判官看一遍」。
2026 年的做法更进一步：**派一队专门唱反调的 Agent 去证伪每一条发现**，只有活下来的才展示。

**行业做法（这是今年最明确的一次收敛）。** 四家厂商、四个名字、同一个架构：

> Claude Code 的 dynamic workflows、Google Antigravity 的 manager、
> Codex 的 thread-level delegation、微软的 Chain of Debate ——
> 全是「确定性脚本扇出 → 多个 Agent 从不同角度攻 → 另一队专职反驳 → 收敛后才给你看」。

关键洞察：**扇出很容易，难点在「反驳那一半」。**
现在这代 harness 幻觉更少，不是因为基座模型更强，而是因为
「一个似是而非的发现，在到你眼前之前已经被三个被要求证伪它的 Agent 杀掉了」。

arXiv 同期还有一篇论文论证：**验证是独立的 scaling 轴**，在更强的 verifier 上花算力，
可能胜过扩大 generator。

**怎么做。** 在现有 `judge.py` 之上加一层，改动很小：

```
judge（现状）：1 个复核者逐条判 → 留/删
加一层：对每条「保留」的发现，起 2–3 个 refuter
        每个 refuter 的指令只有一句：找出这条发现站不住的理由
        存活规则：至少 1 个 refuter 判「无法反驳」才展示
```

**必须配预算闸门**（行业一致警告：扇出烧 token 很快，不设上限会悄悄跑出账单）。
项目已有 `budget.py`，直接复用。

**为什么值。** 这是**唯一能用现有架构低成本实现、且直接提升精确率**的方向。
项目现在复核口径 P=95%，自动口径 P=80% —— 差的那 15pt 里，
相当一部分是「似是而非」的发现，正是 refuter 的靶子。
而且它能直接产出一个可报告的实验：「加 refuter 前后，精确率变化多少」。

**工作量**：小（约 200–300 行）。**性价比最高的一个。**

### 方向 5：MCP Server 化（对外可集成）

**缺什么。** 能力全锁在自己的 HTTP + 前端里。别的 Agent（Claude Code、Cursor）没法调用它。

**行业做法。** MCP 在 2026 年已成为事实标准：10,000+ 公开 server、
SDK 月下载量近亿、Linux Foundation 治理、OpenAI/Google/Microsoft 全部原生支持。
2026-07-28 版规范把核心改成**无状态**（任意请求可落到任意实例，普通负载均衡即可），
新增 Tasks（长任务异步）与 MCP Apps（工具返回可交互 UI）。

**怎么做。** 项目已有的工具注册表天然就是 MCP 的 `tools` 语义，
加一个 `harness/mcp_server.py` 暴露 stdio / HTTP 两种传输，约 300 行。

对外暴露的工具（选少量高价值、只读优先）：

| MCP 工具 | 说明 |
|---|---|
| `audit_repo` | 对仓库跑一次审查，返回发现列表 |
| `who_calls` / `impact` | 转发方向 2 的代码图查询 |
| `detect_changes` | 把 diff 映射到受影响范围 |

**安全边界必须写死**：默认只读；`apply_patch` 类写工具**不暴露**给外部调用方，
或者必须显式配置才开。这与项目既有的「架构助手 `can_edit=False` 硬契约」一脉相承。

**为什么值。** 它把项目从「一个独立工具」变成「生态里的一块」。
对赛题的意义是**展示架构的可组合性**——这正是「可插拔」主张的延伸证明。

**工作量**：中（约 300–400 行）。

### 方向 6：CI / PR 集成 + 可观测性

**缺什么。** 没有 `.github/`，只能本地手动跑。评审看不到「这东西怎么装进真实流程」。
另外，运行过程虽然有事件流，但没有**成本/时延的可视化**。

**行业做法。**

- **CI 集成**：GitHub Action 触发 `pull_request`，取 diff（不取全仓库），
  结构化输出 → 贴 PR 评论。要点只有三条：
  ① 权限最小化（`contents: read` + `pull-requests: write`）；
  ② 只审 diff，超过 ~800 行就先提示「PR 太大」而不是硬审；
  ③ **必须给模型一个「没问题就说没问题」的出口**——否则它会编意见，
  机器人一旦狼来了，一周内就被静音。
- **增量 + sticky**：`incremental: true` 避免重复内联评论；
  `sticky_summary: true` 避免每次 push 都刷一屏。
- **可观测性**：行业标准是 trace 里必须能看到 ①每步输入输出与时延 ②按模型/会话的成本
  ③评测分数趋势 ④失败率分布。开源方案 Langfuse / Phoenix / Opik。
  **本项目不需要引第三方**，已有事件流，补一个成本/时延面板即可。

**怎么做。**

1. `.github/workflows/review.yml`：PR 触发 → 取 diff → 调本项目的 CLI 模式 → 贴评论
2. 前端已有的运行账本（轮数/token/缓存命中/耗时）**升级成趋势视图**：
   同一仓库多次运行的指标曲线，能看出「这个仓库的缺陷在变多还是变少」
3. 输出 SARIF（GitHub 原生认这个格式，代码扫描结果直接标注在 PR 文件行上）

**工作量**：小（YAML + 一个 CLI 入口约 200 行）。**对评审的观感收益很大**——
它证明这东西真能进团队流程，而不只是本地玩具。

## 三、行业水位证据（本节是上面判断的依据）

### 3.1 代码审查的四代架构，本项目在哪

| 架构 | 代表 | 能力边界 | 本项目 |
|---|---|---|---|
| ① 只看 diff | Cursor Bugbot | 抓不到「改了返回结构，三个调用方坏了」 | 已超越（有 diffmode + 局部展开） |
| ② diff + 局部展开 | 多数工具 | 能抓中间带 | ✅ 当前处于这一层 |
| ③ 全仓索引 | Greptile / Qodo / Augment | 跨文件深度，代价是索引延迟（40 万文件约 25 分钟） | ❌ 缺（方向 2） |
| ④ Agent 运行时检索 | Copilot（2026-03 起）/ Anthropic Code Review | 无预建索引，用工具现场探索，代价是 token 不可预测 | ✅ 本项目正是这一层 |

**结论**：本项目的架构选择（④）与 GitHub Copilot 2026 年 3 月转过去的架构一致，
方向是对的。缺的是**把 ④ 的检索质量提上去**（方向 2 的代码图），以及**验证闭环**（方向 1）。

### 3.2 脚手架比模型更重要（这条对我们最有利）

同一批 SWE-bench 数据里反复出现的结论：

- 同样的 Claude Sonnet 4.5，换脚手架，分数从 43.2%（SWE-agent v1）到 59.8%（Cline），**差 16pt**
- 顶级系统的共同点不是模型更强，是：**先做仓库理解**（文件依赖图、相关模块、受影响路径）、
  **迭代精炼**（生成→评估→修订，有的迭代 3–4 次）、**测试驱动验证**
- 多 Agent 架构稳定优于单 Agent；前沿模型做规划、便宜模型做搜索/执行的分工能降本保质量

**对我们的意义**：这直接支撑赛题「AI 技术深度」的叙事——
我们不需要更强的模型，我们需要把脚手架做到位。方向 1/2/4 本质都是脚手架。

### 3.3 验证是新的护城河（2026 的共识判断）

多篇独立材料指向同一结论：

- 「2026 年 Coding Agent 的竞争焦点，已经从生成能力转移到验证能力」
- 「竞争护城河从『谁能生成最多代码』转向『谁能证明代码可上生产』」
- Sonar 的 Foundation Agent 登顶 SWE-bench（79.2%），关键设计是
  **测试驱动补救 + 结构化符号搜索 + free workflow**（放弃僵硬的多阶段流水线）

**真正稀缺的技能**也从「会写代码」变成**「能把什么叫做对讲清楚」**——
哪些流程不能坏、哪些边界必须处理、什么时候该报错而不是静默失败。
这些要写成测试、写成给 Agent 看的规范。这与项目已有的「技能文档按需检索」机制天然契合。

### 3.4 一个反直觉的警告（值得写进报告）

> SWE-bench Verified 上，**7.8% 的「通过测试」补丁其实通不过开发者自己写的测试套件，
> 29.6% 引入了行为偏差**。测试欠约束时，「测试通过」是被高估的证据。

这意味着：方向 1 的验证闭环**不能只跑「那条失败的测试」**，必须做
「B 状态回放 + 范围校验 + 受影响子集回归」。否则验证本身会变成新的假阳性来源。

这条要写进文档和演示里 —— 它证明我们不只是「加了功能」，而是**知道这个功能的失效模式**。

## 四、排期建议（按依赖关系）

```
第一批（能直接提升报告数字，2 周内可完成）
  方向 4 对抗性复核  ← 性价比最高，200–300 行，直接改善精确率
  方向 6 CI 集成     ← 200 行，观感收益大

第二批（补核心缺口，是第三批的前置）
  方向 2 仓库级代码图  ← tests_for / impact 是方向 1 的输入

第三批（依赖前两批）
  方向 1 验证闭环      ← 依赖方向 2 的 tests_for
  方向 3 多语言        ← 可与方向 1 并行，互不阻塞

可选（加分项，非必需）
  方向 5 MCP Server    ← 展示可组合性，但不改变核心指标
```

**判断依据**：先做能**直接改善已报告指标**的（方向 4 能报精确率变化），
再做**改变能力边界**的（方向 1/2 能让「修复」这件事第一次成立），
最后做**锦上添花**的（方向 5）。

## 五、不建议做的（避免踩坑）

| 想法 | 为什么不建议 |
|---|---|
| 接向量数据库 / embedding 索引 | 破坏「零依赖、可审计」定位；结构图能解决 80% 的检索需求，成本低一个量级 |
| 让模型自己判断要不要跑测试 | 模型只会说「我已检查」。验证必须由确定性代码驱动 |
| 追求「支持 20 种语言」 | 规则深度会全线摊平。诚实做法是「非 Python 只承诺粗筛 + 标注置信度」 |
| 无上限的多 Agent 扇出 | 行业一致警告：token 会悄悄跑出账单。必须配 `budget.py` 的硬上限 |
| 靠调 prompt 提升效果 | 脚手架 > 提示词。同模型换脚手架能差 16pt，调 prompt 通常只有 1–2pt |
