1项目概述

1.1 一句话说明

Margin 是一个面向研发流程的 AI 工作台：它把「读代码、找问题、讲结构」这类需要长时间专注的工作 交给一组可插拔的 AI 助手，并用一套统一的界面承载它们的产出。 当前内置两个助手 —— 代码审查（产出带证据的发现列表）与 架构设计（产出可评审的分层蓝图）。

1.2 要解决的问题

研发过程中有两类高价值但耗时的智力劳动，长期依赖资深工程师的时间：

问题传统做法的困难本项目的做法
代码审查
找缺陷、看资源生命周期、查边界条件		 人工逐文件阅读，成本高且不稳定；简单静态扫描工具只能覆盖规则化问题，误报多、无法理解语义 让 Agent 带着工具循环读代码（读文件、搜符号、看 diff、跑规则）， 产出的每条发现都必须带文件与行号证据，并按严重级归类
架构理解与设计
接手陌生仓库、评审分层与依赖		 需要通读大量代码才能画出结构图；口头结论无法沉淀，评审时缺少可讨论的载体 让只读的架构助手产出分层图 + 组件清单 + 关键决策 + 开放问题， 每条决策写明「放弃了什么、代价是什么」，形成可评审的方案草稿

3系统架构设计

整个系统的设计围绕一条主线：把 AI 的不确定性关进工程结构里。 下面按「分层 → 抽象 → 界面 → 事件 → 决策」展开，每条关键决策都注明替代方案与代价。

3.1 总体架构

3.2 Agent = Model + Harness

项目的核心抽象来自一个判断：模型本身不可编程，能编程的是它外面的那层骨架。 把这层骨架（Harness）设计好，同一个模型就能稳定地完成不同任务。 Harness 由五部分组成：

组成职责本项目的实现
上下文管理决定模型每一轮看到什么：静态前缀 + 动态追加系统提示与核心工具定义恒定；进度、状态、检索到的工具 schema 追加到轨迹末尾
工具接口把能力以模型能理解的方式暴露JSON Schema 参数；描述写「何时用 / 何时不用」；数组参数显式声明
约束限制行为边界，防止失控迭代上限、重复调用检测、连续被拒熔断、命令白名单、只读助手硬契约
验证检查产出是否可信三层核验（位置 → 判官 → 证据与权衡）+ 确定性规则交叉验证
纠正出错后给出可操作的修复路径错误信息四层（类型 + 参数 + 调用栈 + 建议）；失败显式而非伪装成空结果

3.3 前端工作台

前端不做「一个助手一套页面」，而是一套骨架 + 声明驱动的差异：

  • 骨架共享：助手轨道 + 上下文栏 + 工作台 + 输入坞，所有助手走这套结构
  • 差异来自声明：助手清单由后端 GET /api/agents 下发， 前端据 outcome 选产出渲染器、据 capabilities 决定显示哪些入口 （例如只有声明了 diff 能力的助手才出现「增量」开关）
  • 强调色只是声明里的一个色值：body[data-agent] 注入 --agent， 深浅三档由 color-mix 派生 —— 接新助手只换一个色值
  • 兜底渲染器：不认识的产出形态按字段原样列出，不白屏、也不假装它是发现列表

3.4 事件流：一条路径同时服务「实时」与「重放」

运行过程中的每一步（开始、决策、工具调用、产出、重试、压缩、完成）都以事件形式追加到运行记录。 SSE 连接先补发历史事件、再实时推送，因此「打开一条正在跑的运行」与「回放一条已完成的运行」 走的是同一条路径 —— 不存在两套渲染实现。

运行产生事件 → 追加到记录（带序号） → SSE 补发 since 之后的事件 → 实时推送新事件 → 前端 applyEvent

3.5 关键架构决策

决策替代方案与为什么不选代价
标准库实现 HTTP 层FastAPI/Flask 更省事，但引入依赖链；安全类工具需要可审计需手写路由、分块传输、SSE 终止序列（都踩过坑）
静态前缀恒定把时间/进度写进系统提示更直观，但会让 KV 缓存整轮失效动态信息必须另想办法追加（状态栏）
产出落类型化桶统一用自由文本更灵活，但无法按形态渲染每加一种形态要写 schema 与渲染器
未知助手直接报错回退到默认助手更「健壮」，但会产出答非所问的结果调用方要处理 400
判官只删不加让判官也能补充会更「完整」，但那等于把审查者与被审者合成一个角色漏报无法由判官补回（可接受：宁可漏也不加噪声）

3.6 技术选型理由

  • Python 3.12：`ast` 标准库足以做结构化代码分析，无需引入解析库
  • httpx 作为唯一运行时依赖：同步调用 + 超时 + 连接池，比 urllib 更可控
  • 原生 JS/CSS 前端：无构建、无 npm 依赖，评审者可 clone 即读；对工具类产品， 这比框架带来的开发效率更重要
  • OpenAI 兼容协议：业界事实标准，换供应商只改三个值

4AI 技术方案

本章是文档的重点：一个能跑起来的 AI 应用与一个可靠的 AI 应用之间的差距， 几乎全部落在这里 —— 上下文怎么组织、工具怎么设计、失控怎么兜住、产出怎么验证。

4.1 模型集成

4.1.1 集成方式

模型调用集中在单一客户端模块（harness/model.py），对上层暴露 「给消息与工具，返回一次决策」的接口。这样重试策略、退避、用量统计、 错误分类只写一遍，Agent 循环里不掺协议细节。

能力实现要点
失败重试只对可重试错误（限流、网络、5xx）重试；指数退避；重试以事件推给界面（用户看到「在重试」而不是卡住）
用量统计累计输入 / 输出 / 缓存命中 token，随运行结果归档 —— 成本可回溯
工具调用走 function calling 通道；参数解析失败时归类为参数畸形并给出重试指引
降级没有 API Key 时切到启发式模型：仍走完整 Agent 循环与工具协议，产出由确定性规则给出

4.1.2 只填三项的接入设计

协议固定为 OpenAI 兼容，因此配置只需三项：接口地址、API Key、模型名称。 其余差异都能从这三个值推出来，不需要用户选「提供商」。

真实操作系统如何处理
贴完整请求地址
https://x/v1/chat/completions		自动裁成根地址。不裁会请求 /chat/completions/chat/completions —— 一个会被误判成「服务挂了」的 404
只写域名 api.x.cn/v1按公网 https / 本机内网 http 自动补协议
自建服务用任意 Key
（vLLM / Ollama）		不强求 sk- 前缀：前缀不是任何协议的要求，强求等于把合法配置挡在门外
模型名写错测试连接返回「接口可达，但列表里没有这个模型，可用：…」，并不判失败 —— 有些服务不实现 /models

4.2 Agent 循环设计

组装上下文 → 请求模型决策 → 执行工具调用 → 观察结果入轨迹 ↺ 收尾（三层核验）

4.2.1 规划：把「打算怎么做」显式化

助手被要求用任务清单工具（update_todo）写下计划并更新状态。 显式计划让「读了三个文件就下结论」这种偷懒行为变得可见，也让用户能中途判断方向。

4.2.2 工具调用：能力按需可见

工具集分两档：核心工具进静态前缀，随叫随到；扩展工具需先检索再加载 schema。 这解决两个实际问题：上下文占用（二十多个工具定义全量前置会吃掉可观预算）、 选择质量（候选越少选错越少）。

4.2.3 收敛：轮次预算

实测发现「撞上限」的根因不是能力不足，而是模型不知道自己还剩几轮。 因此每轮把进度写进状态栏，按剩余比例分三档：

剩余比例提示强度理由
> 40%只报数字不打扰，避免过早收尾
20%–40%「可以开始收尾」剩余轮次优先留给补证据与写代价，而不是继续扩大阅读
≤ 20%「立刻 finish，未覆盖的写进开放问题」半份产出比明确声明「未完成」更糟 —— 评审会以为那是全部
踩过的坑（真实记录）。早期熔断用「累计被拒次数」判定，一旦打开就再也不会关闭， 模型被自己的护栏锁死 —— 连 finish 都被拒绝。 现在改成判据是连续被拒次数（成功一次即归零），且收尾与产出类工具走前缀豁免。 教训：护栏必须可恢复，否则它就是故障源本身。

4.3 Prompt 工程

4.3.1 分层结构

层内容为什么放这里
身份与目标你最擅长什么；本次任务的判据最先进入上下文，决定整体基调
工具契约核心工具定义（何时用 / 何时不用）恒定不变，可被缓存

风格与格式产出字段要求、语言放最后，不占早期注意力

4.3.2 工具描述的三条规矩

  • 必须写「何时不用」：只写能干什么，模型会在不合适的场景使用它
  • 数组参数要在描述里明说：schema 声明 type: array 不够 —— 实测模型连续 5 次把数组字段填成字符串。描述必须写「数组，每项一个…」
  • 错误信息给出目标形态：不只是「类型错误」，而是「即使只有一项也要写成 ['…']」

4.3.3 用「照妖镜」防背诵式作答

架构助手最典型的失败是「背架构图」：把教科书里的通用结构套上去，而不是读代码。 因此在任务说明里直接点出该仓库的照妖镜，例如对 requests：

requests 本身不实现重试，重试在 urllib3 的 Retry。 如果你的方案里出现了「重试层」，说明你没读代码。

评估时这条会被机器检查：参考蓝图里声明了 must_not_contain， 命中的组件会被单独告警 —— 这类「多报了一个不该有的东西」靠精确率抓不住重点。

4.4 工具接口设计

工具作用设计要点

read_file读文件（带行号）支持分段；行号前缀为证据引用服务；offset 越界显式报错

4.5 上下文预算与压缩

  • 预算对象统计静态前缀、历史轨迹与工具输出的 token 占用
  • 压缩触发：占用达窗口 80% 时，对较早的工具输出做摘要化，保留结论与证据，丢弃大段原文
  • 截断提示：单个输出过大时落盘并在上下文里只给摘要与路径，同时明确标注「已截断」，避免模型以为拿到了全部
  • 统一硬上限：读文件、搜索、列表全部有显式上限，且**上限生效时必然告知** —— 静默截断会让模型得出「全仓都没有」的假结论

4.6 缓存感知的上下文结构

这是成本与延迟上的关键优化，做法简单但需要纪律维持：

恒定的静态前缀
系统提示 + 核心工具定义，顺序与内容永不变化。任何动态内容（时间、进度、状态、 按需加载的工具 schema）都追加到轨迹末尾，绝不插进前缀。
为什么有效
主流模型服务按「前缀相同的最长部分」计费与加速。前缀稳定时，每轮只有尾部新增部分 需要重新计算 —— 本项目实测 KV 缓存命中约 87%。
维持这条纪律的难点。「把当前时间放进系统提示」是很自然的写法，但它会让前缀每轮都变， 缓存全部失效。因此这类信息统一由「运行时状态栏」追加在轨迹尾部， 并以自检方式暴露前缀指纹，防止后续改动无意破坏这个不变量。

4.8 规则与模型的交叉验证

「能确定性判定的就不交给模型」—— 规则集既独立产出，又作为模型结果的验证器： 规则命中而模型未报标为疑似漏报，两者都报则提高置信度。 实测中这一机制把规则难以覆盖的语义类缺陷与模型容易忽略的机械模式各自补齐。

4.9 结构化产出

产出不是自由文本，而是有 schema 的结构化数据，落进按类型分桶的容器：

助手产出形态字段
代码审查findingsseverity · file · line · title · detail · evidence · fix · diff
架构设计blueprintlayer（名称/职责/证据）· component（职责/依赖/失效模式/证据）· decision（决策/备选/代价/证据）· open_question（问题/影响/是否阻塞）

结构化带来三个直接好处：前端能按形态渲染；产出能被机械核验（见 4.10）； 评估可以逐条比对答案键。

4.10 三层质量约束：确定性核验 → 独立判官 → 证据审查

本节是本项目在 AI 可靠性上的核心工作。三层按成本从低到高排列，前一层的输出是后一层的输入 —— 先用零成本的方式把明显站不住的挡掉，再花钱让模型复核剩下的。

模型产出 → ① 位置真实性核验
0 成本 · 确定性 → ② 独立判官复核
1 次模型调用 → ③ 证据与权衡审查
0 成本 · 确定性

4.10.1 第一层：位置真实性核验（零成本，确定性）

最初的 verify_citations 只核对「引用的文件读过没有」，不核对 「引用的那一行是否真的在支撑这条描述」。这正是「看似专业但其实错」的软肋。 现在直接读真实文件判断，三条判据（任一成立即通过）：

  1. 引用行里出现了描述中的技术线索（关键词族，如 shell / 加密 / 资源释放 / 越权）
  2. 引用行邻近上下文里出现了该线索（缺陷常写跨多行表达式）
  3. 引用行含描述提到的标识符（函数名、变量名）

行号越界（文件被改写或纯编造）、文件不存在、指向空行或纯注释，一律判不可信。 这条判据是实测出来的，不是想出来的：

三轮修正记录。第一版对 4 条人工构造的假发现只拦住 1 条 —— 原因是关键词族里放进了裸的「query」「拼接」，它们也出现在无关描述里。 收紧后仍有 1 条漏过（指向空行，却靠邻域里的线索蒙混过关）。 最终判据改为「线索命中且引用行本身不是结构行」才 4/4 全部拒绝， 同时保证 20 条真实发现零误杀。

4.10.2 第二层：独立判官（只删不加）

运行收尾前，把每条发现连同它引用的真实代码（带行号）交给一次独立判断： 只问「这段代码能证明这个结论吗」，答 drop 或 keep。

设计约束理由
只删不加让判官既能删又能加，等于把审查者与被审者合成一个角色 —— 正是共享盲区
先做位置核验再送判官位置站不住的发现不进判官：省 token，也避免对着无关代码猜
失败即保留全部判官是降低误报的增强项，不是正确性前提。它挂了就清空结果，会把一次网络抖动放大成「什么都没查到」
输出不可解析也保留全部漏判不等于判错

实测效果：在 vulnerable-service 上，两条「结论与代码相反」的假发现被准确剔除， 并给出具体理由（「第 22 行已是 max(0, ...)，已有下界保护」）； 20 条真实发现零误杀，耗时 7.3 秒。

一个必须记下的发现：判官口径与标注口径并不相同。 在边界条件靶场上，判官删掉了两条真实缺陷，理由是「LIMIT - hits 返回负数在数学上是对的」 「闭区间是设计选择」。判官按「代码是否写错」判断，而标注按「前提是否被约束」判断 —— 两者不同维度。于是加了一道确定性闸：低置信度提示只有在判官明确指出 「代码里没有这回事」时才允许删，其余情况保留。修正后召回从 80% 回到 86%，精确率不变。

4.10.3 第三层：证据与权衡审查（零成本，确定性）

架构产出的性质与缺陷不同：它说的是「这个层 / 组件存在于这里」，关键词族对不上。 因此换判据，但沿用同一个原则 —— 能确定性判定的绝不交给模型。

证据核验

四类产出（层 / 组件 / 决策 / 开放问题）都带 evidence 字段，格式是完整相对路径加行号。 三档核验结果：

状态含义处理
ok路径存在、行号在范围内、指向代码而非空行/注释计入「可精确定位」
weak只有文件名（需补全路径），或指向空行与纯注释提示补全，不判死 —— 有些架构事实确实由注释声明
bad文件不存在或行号越界这条产出没有依据

「没给证据」与「证据是错的」分开统计：前者是遗漏，后者是编造，性质不同。

权衡真实性

业界公认最难识别的失败模式：模型能为任何选择写出流畅理由，把「单纯的偏好」包装成 「严谨的权衡」—— 表面过关，底下没通过。两条确定性规则逼近它：

  1. consequences 必须含负面信号；只有好处没有代价的选择，通常不是选择，而是还没想清楚
  2. alternatives 里至少有一条写出了它自己的优点 —— 只有缺点的备选是稻草人
这条检查也被真实产出打过脸。初版只查「成本 / 风险 / 复杂度」这类名词， 结果在 requests 案例上把 4 条写得很好的决策全判成「只写好处」。原文是这样的： 「依赖图里是假边：只在类型检查期存在，运行时不存在」「必须穷举 urllib3 各版本的异常类型」 「多线程共享同一 Session 时无锁保护」—— 一句「成本」都没有，但都是实打实的代价。 于是改成三条件联合（没有负面词 且 没有转折结构 且 短到不像认真写过）， 并把稻草人判据从「逐条备选都要有优点」改成「整条决策至少一条有优点」。 修正后三案 21 条决策零误报，同时四类真问题仍全部能抓到。

4.10.4 三层合起来的效果

指标改造前改造后
架构证据可精确定位率9%（55 处引用仅 5 处写全路径）95%–99%（三案例实测）
编造/错位引用未检测0（bad 计数为 0）
小靶场精确率76%76%（小样本本就没有多少误报可删）
小靶场召回86%86%（加低置信度保护前会掉到 80%）

诚实结论：三层核验在大样本上收益明显（证据可核验率从 9% 提到 95% 以上）， 在小样本上几乎无收益（小样本误报本来就少），但会带来误删风险 —— 所以低置信度保护是必要防线。 不夸大它，也不因为「没测出提升」就撤掉它。

5核心功能实现

5.1 代码审查助手

一次审查的完整链路：

选仓库 → 描述重点 / 勾选范围 → 运行（可实时观察） → 三层核验 → 发现列表 + 可回放

每条发现都带：严重级别、文件与行号、复现证据、修复建议，若涉及代码改动还会给出建议 diff。 列表支持按严重级别筛选，计数随产出实时增长。

5.2 架构设计助手

架构助手是只读的（can_edit=False），工具集里没有写工具 —— 这是硬契约，声明与能力不允许脱钩。产出为分层蓝图：

产出要求
分层每层说清「负责什么」与「不负责什么」；层数宜少不宜多，超过 5 层通常是误把模块当层
组件必须写「为什么这样切」；依赖只写已确认存在的
决策必须写放弃了什么与代价；「先这样以后再改」尤其要留下当时的前提
开放问题不确定的必须登记，不许用肯定语气掩盖

界面把四条产出的代码依据做成可复制的路径标签，底部是证据核验面板 （可精确定位率、ok/weak/bad 分布条、分类型明细、问题清单）。

5.3 增量审查

商用审查工具的真实工作模式是只审 PR 改动。本项目实现为：

解析 unified diff → 抽被改符号 → grep 反查调用点 → 合成审查简报

关键设计：只定位不判断（判断归模型、判定归判官），以及 反查改动之外的调用点 —— 这是增量审查最有价值的部分， 因为作者往往没打开那些文件。实测改动一个函数后，准确找出了未在 diff 中的调用点。

拿不到 diff 必须报错，不能静默退化成全仓审查。 用户以为自己在审增量、实际审了全仓，这种偏差比报错难发现得多。

5.4 多助手隔离

「可插拔」若只是切换图标，会产生一类难发现的问题：切到架构助手，侧栏里还是审查记录。 本项目从三处隔离：

  • 服务端过滤：/api/runs?agent= 与 /api/repos?agent=，各自只返回自己的记录
  • 计数同口径：仓库卡上的运行次数与会话列表必须用同一处过滤逻辑，否则会出现「写着 5 次却点不出来」
  • 正文归属：正文区归当前选中的那一条会话独占，切换时先清空再加载，避免两次运行的内容拼接

5.5 账号与会话安全

项实现
密码存储scrypt（n=214, r=8, p=1）+ 每账号随机盐，存 scrypt$n$r$p$salt$hash
比较方式hmac.compare_digest 常量时间比较，防时序攻击
登录失败不区分「用户不存在」与「密码错误」—— 否则接口变成账号枚举器；连续失败 5 次锁 60 秒
会话只存服务端内存，Cookie 为 HttpOnly + SameSite=Strict；刻意不加 Secure（本机 http 加了浏览器就不发送），注释里写明对外服务必须同时上 HTTPS
落盘账号表原子替换写入；文件损坏时改名留档而非静默清空

5.6 前端设计系统

视觉方向是「玻璃仪表台」。核心是一条结构性规则，而非审美偏好：

材质用在哪为什么
玻璃
blur + 上缘内高光 + 发丝边界		顶栏、输入坞、模型菜单、弹层、运行条这些是「浮在内容之上」的东西
实体
实心表面 + 1px 边界		发现卡、工具步、计划项、蓝图节点这些是「内容本身」
为什么不能全用玻璃：毛玻璃铺满每个卡片，层级就全平了 —— 屏幕上所有东西都在发虚光， 眼睛找不到落点。这条规则写在贡献指南里，并有测试断言守着。

配套：深色为默认、浅色是同构覆盖（不是两套样式）；字体三族分工（Sora / Instrument Sans / JetBrains Mono）；数字一律 tabular-nums；过渡只命名改变的属性，禁止 transition: all； 图标按钮视觉 36px、热区补到 44px。

6.2 评估体系

6.2.1 靶场与链路

12 个靶场 → 批量运行 → 机器可读结果 → 人工复核 → 报告（脚本现算）

12 个靶场、134 条标注。其中 8 个是难度刻度（s1–s8，平均 2 文件 / 62 行）， 3 个是规模刻度（m1–m3，1300–1800 行，含跨文件调用链与刻意埋设的干扰项）， 1 个综合样本（6 文件 / 231 行 / 23 条标注）。

为什么要分开两种刻度。小样本上测出的分数会系统性偏高： 同一个综合样本，F1 从 8 个小靶场的 82% 掉到 70%。 只在小文件上验证，等于只测了最容易的场景。

6.2.2 实测结果

口径召回率精确率F1
自动匹配（同文件 + 行号 ±2，8 小靶场）86%80%82%
人工复核（逐条判定，带理由）97%95%—
规模刻度（m1–m3，1300+ 行）74%72%72%
确定性规则基线（对照）32%——
为什么要给两个口径。自动匹配用「同文件 + 行号容差」判定，会产生三类系统性误判： 同一缺陷行号略有不同（被算成一漏一多）、模型指出的真问题不在答案键里（被算成误报）、 相邻缺陷互相顶替。只报对自己有利的那个口径，等于把度量方式伪装成能力差异。

6.2.3 度量本身的纪律

  • 度量工具出 bug 时先怀疑度量。本项目发生过两次：一次匹配逻辑重复消费标注， 召回被低估约 10 个百分点；一次分组口径把冗余算成误报，精确率从 100% 掉到 58%。 两次都不是模型的问题。
  • 指标对行号容差高度敏感。整体 F1 在容差 ±0 时为 61%，±4 时升到 95% —— 报单一容差下的数字没有意义。
  • 单次跑分不可引用。同一靶场三轮的召回波动可达 100/100/50。 选型类结论必须跑 3–5 次看均值与波动。
  • 任何口径算出精确率或召回 > 100%，立刻停手查分母。 本项目确实发生过一次：用宽容差统计时得出「召回 96% / 精确 110%」， 说明同一条发现被反复计入覆盖多条标注 —— 口径在自欺欺人，当场推翻改报区间。
  • 标注要拿真实运行结果对照补全。「先写标注再跑模型」会把精确率系统性低估： 同一天在三个大样本上分别低估到 30% / 22% / 31%，逐条读源码核实后修正到 83% / 56% / 77%。
  • 报告不手抄。文档里的数字由脚本从原始结果现算，避免手抄与数据脱节。

6.3 架构助手难度实测

针对架构助手单独设计了难度刻度，用三个真实开源仓库验证能力边界 （pluggy / requests / celery，规模 7k / 12k / 123k 行）。上游代码不入库， 由 arch-cases/fetch-cases.sh 按需克隆 —— 这是许可证边界，也是仓库体积问题。

一个反直觉的发现。初版参考蓝图只收「教科书级事实」（Session 三合一、mount 可替换）， 结果两个案例的决策维度命中 0 条。打开产出后看到模型给的是 「bootsteps DAG 动态装配」「公共 API 惰性模块代理」「fast_trace 快路径」—— 比参考蓝图更深入。问题不在模型，在评分标准只认概念层、不认实现层。 合并两类条目后才反映出真实水平。

7创新点说明

7.1 技术创新点

创新点 1：三层质量约束 —— 把「可信」拆成可执行的检查

AI 审查工具最大的问题不是找不到问题，而是找到了一堆站不住的问题。 本项目把「可信」拆成三层按成本递增的检查：零成本的位置真实性核验、 一次模型调用的独立判官、零成本的证据与权衡审查。 每层的判据都是确定性优先，且每条判据都被真实数据反向修正过（详见 4.10）。

其中「判官只删不加」「判官失败保留全部」「低置信度需明确反证才允许删」三条约束， 解决的是一类很隐蔽的失败：过滤器本身变成了故障源。

创新点 2：助手即声明（Agent as a Declaration）

把「一个 AI 助手」抽象成一份声明：标识、系统提示、工具工厂、产出形态、强调色、只读边界与能力标记。 接入新助手只需写这份声明并注册，工具层、渲染层、HTTP 层、前端轨道都不需要改动。 声明是可执行的契约 —— 声明只读的助手若注册了写工具，运行会在启动时直接失败。 前端也不按助手 id 硬编码，而是读清单里的 outcome 与 capabilities 决定渲染与入口。

创新点 3：产出形态由助手声明，渲染层注册表 + 兜底

产出不是「统一都叫发现」，而是由助手自己声明形态（发现列表 / 分层蓝图 / 其他）， 渲染层按注册表分派，未注册的形态走通用兜底。这消灭了一类很难发现的问题： 把「渲染器不认识」说成「产出为空」。

创新点 4：缓存感知的上下文结构

静态前缀恒定不变，一切动态信息追加到轨迹末尾，使 KV 缓存命中率实测约 87%。 项目还把「前缀指纹」做成自检项，防止后续改动无意破坏这个不变量。

创新点 5：轮次预算 —— 让模型知道还剩几轮

实测发现「撞上限」的根因是模型不知道自己还剩几轮，于是边读边画直到用尽。 解决方式不是加轮数，而是每轮把剩余比例写进状态栏，并在 ≤20% 时明确要求收尾。 改造后困难案例从「两次撞 24 轮上限」变为「23 轮正常收尾」。

创新点 6：可审计的零依赖架构

后端 HTTP/SSE 层用标准库实现（外部依赖仅 httpx），前端原生 JS/CSS 无构建。 对一个安全审计类工具而言这不是「简陋」，而是设计选择：依赖越少越可审计、 零安装门槛、不受供应链风险影响。

创新点 7：面向代码场景的检索策略（替代向量 RAG）

代码检索的难点不是语义相似度，而是准确的行号与结构。项目用三条路径替代向量检索： 工具清单渐进披露、符号级读取、一次 ast 扫描产出结构清单（sketch）。 目标与 RAG 一致（在有限上下文里拿到需要的知识），路径更贴合代码场景。

7.2 应用创新点

创新点 8：审查与设计共用一个可插拔内核

把两类差异很大的研发任务（找缺陷 / 讲结构）放进同一工作台，共享同一套运行时、工具协议、 事件流与界面骨架，差异全部由声明表达。这验证了内核的通用性 —— 新增助手不再是「再造一个应用」，而是补一份声明。

创新点 9：架构蓝图的可评审化

架构产出不是描述性文字，而是「分层 + 组件 + 决策（含放弃的方案与代价）+ 开放问题」， 每条都带可核验的代码位置。其中开放问题尤其有价值：它明确标出「当前无法确定、 需要人来定」的部分，把 AI 的边界如实交付给使用者。

创新点 10：面向评审的诚实性设计

一系列刻意的「不假装」：失败必须显式；产出计数不当质量指标；无法确定的问题单列； 渲染器不认识就说认识不了；被中断的运行如实标注未完成；界面不内置任何样例数据 —— 连不上后端时明确说未连接并给出启动命令，而不是渲染一份「看起来跑完了」的结果。

为什么把「诚实」算作创新点。AI 应用最容易赢得短期好评、输掉长期信任的做法， 就是让界面看起来很完整。本项目把「不假装」做成了工程约束：界面不携带假数据、 工具失败必须上报、判官失败保留全部、指标双口径全报。这些选择让演示效果变差， 让可信度变高。

创新点 11：评估驱动开发

自带完整评估链路（靶场 → 批量运行 → 人工复核 → 报告现算），并在开发过程中 反复修正度量本身的错误，最终形成「双口径 + 单次不可引用 + 数字不手抄 + >100% 立即停手查分母」的纪律。项目还留下了与公开基准的对照，明确写出 「哪些结论可以下、哪些不能下」。

8.3 后续计划

  1. 扩大样本：补 500–2000 行、多语言的靶场，让规模效应可测 —— 这是当前最缺的证据
  2. 多轮评测：每档跑 3–5 次取均值与波动，替代单次跑分
  3. 归档脱敏：把 .runs/ 里的凭据与内联密钥做正则脱敏
  4. 语言扩展：接入 Tree-sitter 之类做多语言符号提取，替代只支持 Python 的 ast
  5. 判官迭代：把判官口径与标注口径的差异做成可配置，而不是硬编码
一句话总结。这个项目最有价值的不是「AI 能审代码」，而是把 AI 的不确定性 变成了可以检查、可以讨论、可以反驳的东西 —— 每条产出指向具体行， 每条决策写出代价，每个不确定标为开放问题，每个指标给出双口径。 在这个前提下，「AI 辅助研发」才是一个工程问题，而不是一个期待。
