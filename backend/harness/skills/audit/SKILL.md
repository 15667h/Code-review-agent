# 代码审计方法论

## 这份文档服务谁

服务正在做代码审计的 Agent，以及需要复核审计结论的人。判断的依据是**可验证的事实**，
不是「感觉这里有风险」。

## 先想清楚一件事

审计的产物不是「发现了多少问题」，而是**让读报告的人能独立复现你的判断**。
一条写得含糊的发现，比漏报更有害 —— 它会让读者花时间核查一个不存在的问题，
然后开始怀疑整份报告。

## 核心原则

### 1. 证据优先于推理

每条发现都必须能回答：**「我怎么知道这里有问题？」**

- 好证据：具体的代码行、工具输出、可复现的触发条件。
- 坏证据：「这看起来不太对」「通常建议不要这么写」。

如果你说不出证据，说明你还没查完，**继续查，不要先记录**。

### 2. 静态看代码只能看到一半

阅读代码能发现**结构性问题**（资源没归还、异常被吞、边界写错）。
但下面这些必须靠工具验证，不能靠读：

- 行为是否真的异常 → 跑测试
- 语法是否合法 → lint
- 某个函数是否还有别的调用点 → grep
- 改动是否只影响预期范围 → git diff

**能用工具验证的，一定要验证。** 阅读得出的结论是假设，不是发现。

### 3. 影响面决定级别，不是问题类型

同样是「异常没处理」，在不同位置后果差很远：

| 位置 | 后果 | 级别 |
|---|----|----|
| 请求主路径上的资源获取 | 服务不可用 | blocker |
| 后台任务的日志写入 | 丢日志 | warn |
| 一次性迁移脚本 | 需要重跑 | note |

定级时问自己：**这个缺陷在什么条件下会造成什么后果？** 把条件写进 detail。

### 4. 只报能定位的问题

不能给出 `file:line` 的问题，说明你还没找到它落在哪。
跨文件的问题（比如 A 处写的数据 B 处按不同类型读）**也可以报**，
但要写出两端的准确位置，而不是「某处」。

## 定级标准

- **blocker**：会导致数据错误、资源泄漏、服务不可用、安全问题。
  特征：在正常使用下就会触发，或者一旦触发难以恢复。
- **warn**：在特定条件下出错，或缺陷明确但影响可控。
  特征：需要异常输入、边界条件、或特定时序才会触发。
- **note**：可读性、健壮性、可维护性上的改进。**不要因为它们数量多就拔高**。

宁可少报一个 note，也不要把 warn 写成 blocker —— 分级失真的报告等于没有分级。

## 禁止清单

以下做法会让报告失去价值：

1. **编造行号。** 引用前必须确认你确实读过那一行。引用的行号与实际不符是硬伤。
2. **把推测写成结论。** 不确定就写「需要确认」，不要写「显然」。
3. **记录风格问题。** 命名、缩进、注释、个人偏好的重构，除非它直接导致缺陷。
4. **重复记录同一问题。** 同一个位置同一个原因只报一次；多处同因问题写一条并在 detail 里列出所有位置。
5. **为了凑数而报告。** 如果检查完确实没有问题，就如实说没有问题，并说明检查范围。
6. **夸大影响面。** 只在特定条件下触发就写清楚条件，不要暗示它随时会炸。

## 跨文件问题怎么处理

跨文件的数据流缺陷（类型不一致、状态不同步、契约违约）是价值最高的发现类型，
但也最容易写成含糊的结论。处理方式：

1. 找到**写入端**与**读取端**的确切位置。
2. 记录两端各自的形状（写的是什么类型、读的时候假设是什么类型）。
3. 说明在什么条件下两者会不一致。
4. 以其中一端作为 `file:line` 落点，另一端写在 evidence 里。
