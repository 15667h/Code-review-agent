# 什么样才算证据

## 三类有效证据

### 1. 代码原文（最常用）

必须是**你实际读到的那几行**，含行号。

```
evidence: L45 conn = await pool.acquire()
          L55 await pool.release(conn)   ← 在 L46 的 await 抛错时不可达
```

要点：引用要覆盖「问题成立所必需的那几行」，而不是只引一行。
上面这个例子里，只引 L45 说明不了任何问题 —— 必须同时呈现「归还点在哪、为什么绕不过去」。

### 2. 工具输出

命令、测试、lint 的真实输出。这类证据最强，因为它不依赖你的解读。

```
evidence: pytest -k rate_limit 输出 3 个失败用例：
          FAILED tests/test_rate_limit.py::test_boundary - assert 101 == 100
```

### 3. 可复现的触发条件

当无法直接跑出结果时，给出**确定性的构造方式**：

```
evidence: 构造 t = window_start 的请求，连续两次判定返回的 hits 均为 limit，
          第三次才被拒绝（见 L63 的 `window_start <= t` 为闭区间）。
```

## 不算证据的东西

| 写法 | 为什么不算 |
|---|---|
| 「这样写不规范」 | 规范性不是缺陷；说出具体后果才算 |
| 「可能有并发问题」 | 「可能」不是结论；给出触发时序 |
| 「建议使用 XXX 库」 | 这是偏好，除非能说明当前写法在什么条件下出错 |
| 「与项目其他地方的风格不一致」 | 风格一致性与正确性无关 |
| 「这里应该加个 try」 | 「应该」是建议；说明不加会怎样 |

## 证据与结论的对应关系

写完后自检：**把结论遮住，只看证据，一个不了解上下文的人能不能推出同样的结论？**

如果推不出来，说明证据不足或结论跳步了。这是最常见的报告质量问题 ——
作者心里清楚整条推理链，但写出来的证据只覆盖了最后一环。

## 一个常见陷阱

**不要把「代码看起来能工作」当作「验证过它能工作」。**

```
坏：evidence: 这段逻辑看起来会在池满时阻塞，应该没问题。
```

「看起来」和「应该」都表明你只是在读代码。此时要么去跑一次，
要么把结论降级为「需要确认」并说明未验证。
