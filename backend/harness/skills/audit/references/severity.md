# 分级判据对照

## blocker 的典型形态

| 形态 | 为什么是 blocker |
|---|---|
| 资源在异常路径上不归还 | 占用随异常频率单调增长，最终整体不可用，且重启前不会自愈 |
| 请求主路径上的未捕获异常 | 直接返回 5xx，用户可感知 |
| 凭据硬编码进入仓库 | 一次泄露即永久失效，且无法通过改代码补救 |
| 外部输入直接拼接进查询/命令 | 可被利用，且危害面取决于数据库权限 |
| 状态写入后未落盘 / 事务未提交 | 数据静默丢失，事后无法追溯 |
| 并发下共享可变状态无保护 | 概率性数据损坏，最难定位 |

判定关键：**正常使用下就会触发，或者触发后不可恢复。**

## warn 的典型形态

| 形态 | 为什么不是 blocker |
|---|---|
| 异常被静默吞掉 | 故障会以更晚、更难定位的形式出现，但服务仍在运行 |
| 边界条件写错（闭区间、差一） | 只在边界输入上出错 |
| 可变默认参数 | 只在多次调用同一函数时累积 |
| 重试没有上限 | 依赖下游持续不可用这一条件 |
| 忘记关闭文件句柄 | 通常被 GC 兜住，只在长期运行进程里累积 |

判定关键：**需要特定条件才触发，且影响可控。**

## note 的典型形态

- 生产代码里的 `assert`（`-O` 下被移除，但多数部署并不开 `-O`）
- 与 `True`/`False` 直接比较
- 函数过长、嵌套过深
- 缺少类型注解

**note 不应该因为「多」而被拔高为 warn。** 如果一个仓库里有 200 条 note，
报告的价值在于前 20 条 blocker/warn，而不是把 note 也报成大问题。

## 灰色地带怎么判

有些问题落在两级之间，用这三个问题收敛：

1. **触发条件有多常见？** 需要构造特殊输入才算 warn；日常就会遇到应该算 blocker。
2. **失败是否显式？** 抛异常、返回错误码是显式的；静默算错值是最危险的。
3. **有无人为兜底？** 上游重试、监控告警、人工巡检能不能兜住？兜不住的要升级。

三个问题里有两个偏向严重，就升级一级。

## 一个反例

> 「`find_user` 使用字符串拼接构造 SQL，建议改用参数化查询。」

这条的问题不是结论错，而是**没有说清后果**。更好的写法：

> 「`find_user` 把 `name` 直接拼进 SQL 文本。当 `name` 为 `' OR '1'='1` 时，
> 查询会返回全部用户记录（evidence: `sql = "SELECT ... WHERE name = '" + name + "'"`）。
> 该函数的调用方是登录路径，因此构成认证绕过。」

差别在于：读者能判断这条要不要立刻修、修不修得起。
