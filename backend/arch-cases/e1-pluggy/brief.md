# E1 · pluggy —— 插件系统（简单）

## 难度锚定

系统设计领域的难度刻度有广泛共识（System Design Primer / techscreen 2026 canonical set /
tutorialq framework 都把题目按「概念集群」分 Easy→Hard）：**Easy 档考的是「一个清晰的调用链 +
一两种模式」，不需要分布式、不需要一致性取舍**。pluggy 正落在这一档：

- 单进程、纯同步、无 IO、无并发 —— 与 Hard 档（分布式、fan-out、共识）隔着一整个概念带；
- 但架构是**真的**：插件发现 → 注册 → hookspec/hookimpl 匹配 → 调用链组装 → 包装器织入，
  一条完整链路，且 `pytest` 整个生态都建立在它的抽象上（不是玩具代码）。

## 仓库

- 上游：https://github.com/pytest-dev/pluggy （pytest 的插件内核，1.x 仍在此独立维护）
- 规模：36 个 Python 文件 / 约 7.2k 行（含测试）
- 测试方式：全量（无 scope 限制）

## 给架构助手的目标（原文）

> 为这个插件系统出一版可评审的架构方案：分层、组件、关键决策与未定的问题。
> 重点讲清四件事：hook 调用链是如何被组装与执行的；插件发现与注册的边界在哪里；
> hookspec 与 hookimpl 的匹配规则属于哪一层；这套抽象对宿主（pytest）许下了什么契约、
> 又有哪些地方是刻意不承诺的。

## 评审这份蓝图时看什么

1. **是否识别出 `_hooks` / `_manager` / `_wrappers` / `_result` 的职责切分**，
   而不是把 6 个文件平铺成 6 个并列组件。
2. **调用链的组装时机**（首次调用时还是注册时）有没有说对 —— 这是 pluggy 最关键的设计决策。
3. **决策记录里有没有「被弃方案」与代价**（例如为什么不支持异步 hook、为什么 LIFO 调用）。
4. **开放问题是否点到真实的不确定性**（例如旧式 `hookimpl` 兼容层的债务）。
