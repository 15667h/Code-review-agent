# 架构设计助手 · 三档难度实测报告

> 2026-10-16 · 模型 `deepseek-flash` · 真实 API · 5 次运行（3 首发 + 2 复跑）
> **样本量声明：每档 1~2 次运行。以下结论中凡标注「初步信号」的，都不足以作为选型依据，
> 只作为「下一轮该测什么」的输入。**

## 一、测试设计：难度刻度从哪来

难度分级不是拍脑袋，采用多个权威来源的一致刻度（概念集群决定难度，而非代码量）：

| 档位 | 共识考法（System Design Primer / techscreen 2026 canonical set / tutorialq） |
|---|---|
| Easy | 一个清晰调用链 + 一两种模式；无分布式、无一致性取舍 |
| Medium | 单系统内多层抽象、连接复用、失败重试；限定在单进程单次请求生命周期 |
| Hard | 多进程/多节点、可替换基础设施、失败语义（至少一次/至多一次）、状态机 |

按同一刻度选三个真实仓库（架构要真实存在，不是玩具）：

| 案例 | 仓库 | 上游 | 规模 | scope |
|---|---|---|---|---|
| **E1** 简单 | pluggy | pytest-dev/pluggy（pytest 的插件内核） | 36 文件 / 7.2k 行 | 全量 |
| **E2** 中等 | requests | psf/requests（Python 事实标准 HTTP 客户端） | 37 文件 / 12k 行 | 全量 |
| **E3** 困难 | celery | celery/celery（分布式任务队列） | 447 文件 / 123k 行 | `["celery"]`（只读源码包 161 文件；tests/docs 不承载架构决策，如实声明） |

每个案例的 `brief.md` 里预写了「照妖镜」——蓝图必须答对的具体架构事实。

## 三、结论

### 1. 内容质量：三档都通过了各自的照妖镜 ✅

- **E2 的照妖镜**（「requests 本身不重试，重试在 urllib3」）：蓝图正确写出
  「重试放在传输适配层（urllib3 Retry），重定向与 401 挑战重试放在会话/认证层」。
  把重试说成 requests 自己的一层 = 没读代码，没有发生。
- **E3 的路径完整性**：producer（app.send_task）→ AMQP 消息构造 → broker（kombu）→
  Consumer 蓝图 → Request 分派 → 并发池 → trace → 结果后端 → AsyncResult，九个环节齐全；
  并正确指出 kombu/billiard 为仓库外边界。开放问题问到了真东西：两套任务状态并存
  （结果后端 states vs 请求 states）、acks_late 语义分裂在两层、AsyncResult 跨三层直接依赖。
- **E1 的决策质量**：8 条决策全部命中 pluggy 的真实设计取舍（顺序决策放在注册时刻而非执行时刻、
  project_name 命名空间而非类型校验、不做并发保护也不支持 async hookimpl、旧式 wrapper 并存）。
- 三档都做到了「带证据」：E2 的总结里引了 `adapters.py` 748 行与具体符号名，
  E3 引了 `celery/app/base.py:1192-1226` 行号。

### 2. 产出规模与仓库复杂度没有稳定映射 ⚠️（初步信号）

原本假设「17 倍代码量差 → 产出规模差一个量级」。实测**不成立，且运行间波动大于档位差**：

- E3 两次：9 组件 vs 19 组件（同仓库同 scope，波动 2 倍以上）
- E1 两次：14 组件 vs 12 组件
- 两档产出始终落在同一量级（10~20 组件），没有按 7k/12k/123k 行拉开差距

解读：**组件粒度由模型当时的判断决定，不受仓库规模锚定**。简单仓库（6 个源码模块）报出
12~14 个组件是过度拆分；困难仓库报 9 个时是展开不足。这意味着**不能把「产出规模」
当作难度或质量的代理指标** —— 评审时要点开内容，不能看计数。

### 3. 收敛性随难度下降（初步信号，两轮方向一致）

| 案例 | read_file 次数 | record_component | 收尾 |
|---|---|---|---|
| E1 #2 | 26 | 12 | finished（14 轮内主动收尾） |
| E3 #2 | **43** | 20 | 撞 24 轮上限 |

E3 两次运行一次 finish 一次撞上限；E1 一次撞一次 finish。方向性结论：
**困难案例显著更难在该收尾时收尾** —— 可读的东西多，模型倾向于继续探索。
这对产品是真实风险：用户对复杂仓库跑一次，可能拿到「达到迭代上限」的半成品。

## 四、顺手挖出的两个缺陷（与本测试无关但被它暴露）

1. **`record_decision.alternatives` 数组参数 3 次失败**（E2）：`参数校验未通过：参数
   alternatives 应为 array`。与之前 `failure_modes` 是同一类问题 —— schema 的
   `type: array` 不够，描述必须明说「数组，每项一个…」。同类修过一次，这次是漏网的
   第二个（`todos` 是第三个，静态排查时发现）。
   **已修（2026-10-16 当轮）**：① 错误信息本身给出目标形态（「即使只有一项，也要写成
   ['...'] 的形式」），惠及所有 array 参数而非逐个补描述；② 三个漏网参数的描述补齐；
   ③ 加一条全量测试——两个 agent 的所有工具、每个 array 参数的描述必须含「数组」，
   新增工具忘记写就红灯，不再靠实测发现。
2. **组件名与依赖名不一致导致依赖边丢失**（E2）：`urllib3 PoolManager` 的 `depends_on`
   写了自己（自依赖，旧代码把它当「已知组件」放行）；另一些依赖名与组件名存在大小写/
   空格差异（`Session` vs `session`），后端不做归一、前端按归一找节点 —— 对不上的边
   静默消失，图上缺一块很难事后发现。根因：`record_component` 既不校验自依赖，
   也不把依赖名对齐到已登记组件的规范名。
   **已修（2026-10-16 当轮）**：后端按 `trim().toLowerCase()` 与前端同规则归一，
   命中则改写为规范名；自依赖剔除并在回复里说明；未登记的名字保留但点名提醒。
   回归测试 4 条（含一条「所有 array 参数描述必须自证是数组」的全量检查）。

## 五、下一步该测什么（样本量不够，只列方向）

1. 每档补到 3~5 次，才能把「规模无映射」「收敛性下降」从初步信号变成结论（项目纪律：
   单次跑分不可引用，本次每档只有 1~2 次）。
2. 修掉上述两个缺陷后重跑 E2/E3，对比工具失败率与依赖边完整率的变化。
3. 收敛性问题值得单独做实验：同仓库跑 max_iterations 12/18/24/30，看
   「finished 比例」与「产出完整度」的曲线，给默认值找依据。
